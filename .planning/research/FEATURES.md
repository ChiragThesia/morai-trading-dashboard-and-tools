# Feature Research

**Domain:** Multi-user, broker-connected trading journal — backend only (no UI this milestone)
**Researched:** 2026-08-29
**Confidence:** MEDIUM

## Scope note

The single-user journal feature set — which metrics to show, the entry/close form, the review
surface — is settled in `docs/rebuild-research/trading-journal-research.md` and `PROJECT.md`. It is
not re-derived here. This file covers only the delta: what changes when the journal serves a closed
group of 4-5 known people over their own broker connections instead of one local user, and what an
API-only backend must expose that a single-user local tool never had to.

Every finding below is a web-search digest, MEDIUM confidence unless stated otherwise — general
patterns from vendor docs and engineering blogs, not audited against this project's exact
constraints. Two claims were verified by fetching primary-source pages directly (marked HIGH-source
below); everything else stayed at search-summary fidelity and is flagged as such.

## Feature Landscape

### Table Stakes (Users Expect These)

#### Identity, onboarding, account lifecycle

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Admin-created accounts, no self-serve signup | Standard pattern for invite-only tools at this scale — the admin already knows all 4-5 users; a public signup form invites accounts the system was never built to isolate. | LOW | The admin (owner) creates each account directly or sends a one-time invite link; no public registration endpoint exists at all. Source: Auth0, WorkOS, Userpilot B2B onboarding posts — general pattern, not audited. |
| Session-based login, no email-dependent flows | `PROJECT.md` already requires "log in and stay logged in across sessions." No email infrastructure exists or is planned. | LOW | Standard username+password plus a long-lived session or refresh token. |
| Admin-mediated password reset | No SSPR product surveyed (Entra, ManageEngine, LogonBox) handles the zero-email case — every one assumes email, SMS, or an admin console. At 4-5 known users, the admin console *is* the owner. | LOW | Two workable shapes: the admin rotates a password and hands it over out-of-band (text/Signal), or a one-time setup link is generated by the admin at invite time and reused for reset. No "forgot password" self-service email flow — none is possible without an email service. LOW confidence: no source addressed the zero-email case directly; this is inference from the absence of a fitting pattern. |
| Self-service account deletion | Data-portability norms expect a user can leave and take (or purge) their data without operator intervention, even in a closed group. | LOW-MED | Must cascade through encrypted per-user data key, campaigns, snapshots, audit log retention. Complexity is mostly in the encryption teardown, not the endpoint. |

#### Per-user broker connection

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Per-user Schwab OAuth connect flow | `PROJECT.md`: "User connects their own Schwab account via OAuth, self-service." | MED | Standard OAuth2 authorization-code flow, CSRF `state` as single-use nonce (`NN-35`), per-user token storage under envelope encryption. |
| Connection health as a first-class, queryable state | Comparable products (Tradesyncer, QuantWheel, tradeSteward — retail trading-tool connection managers) all surface a per-account status: healthy / warning / broken, not just "connected: true/false." | LOW-MED | Minimum three states: healthy, expiring-soon, expired/broken. A boolean is not enough because Schwab's 7-day cycle means "connected" is never a stable resting state — it is always counting down. |
| Pre-expiry warning, not just post-expiry failure | Schwab's refresh token expires exactly 7 days after issue, server-side, deterministic (`PROJECT.md` constraints; confirmed independently via schwab-py docs and developer.schwab.com). This is unlike Plaid/SnapTrade, where breakage is unpredictable — Plaid's own webhook set treats the two cases separately: `ERROR`/`ITEM_LOGIN_REQUIRED` reacts to unplanned breakage, while `PENDING_DISCONNECT` fires 7 days *before* a scheduled US/CA disconnection specifically so the app can warn ahead of time (verified by fetching plaid.com/docs/api/items directly — primary source). Schwab's expiry is entirely the "scheduled" case, so the reactive-only pattern (SnapTrade's disabled-connection webhook, fired after the fact) is the wrong half of the analogy to copy. | LOW-MED | Expose `expires_at` per connection (or a cheap `/connections/{id}` status endpoint) so any client can compute and render a warning threshold itself — e.g. "expires in <2 days." No email needed: the user logs into the journal at least weekly to review trades, so an in-app banner on next login is a sufficient channel. |
| Re-auth reconnects the existing link, never creates a duplicate | SnapTrade's reconnect flow explicitly re-establishes a disabled connection by UUID rather than starting a fresh one — the alternative (silently creating a second connection per re-auth) would fragment one user's fill history across two connection records. Source: docs.snaptrade.com/docs/fix-broken-connections (search-summarised; SnapTrade's docs site is JS-rendered and did not yield fetchable static text to verify verbatim — treat the mechanism, not any exact field name, as the transferable claim). | MED | The re-auth endpoint must target the existing `connection_id`/account record, overwrite its stored (encrypted) token, and leave every fill and event already ingested under that connection untouched. |
| Catch-up sync triggered on successful re-auth | A connection that sat expired for N days has a gap. The system needs to know to backfill that gap the moment the connection is repaired, not wait for the next scheduled poll. | MED | Ties directly to the idempotent re-sync requirement below — this is just re-sync triggered by a specific event (successful re-auth) rather than a timer. |
| Per-account "stale for how long" visibility | Snapshots stop silently for a user whose connection lapsed; `NN-16` requires an honest gap, never a fabricated value, but a gap needs to be a queryable *fact*, not just an absent row, or nobody notices the user was dark for three days. | LOW | A derived field (last successful sync timestamp per connection) answers this without new storage. |

#### Data isolation

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Row-level isolation scoped to user id | Standard fit for small-tenant systems: Postgres RLS scoped by a session-derived user id, contrasted with schema- or database-per-tenant (reserved for large/regulated tenants). Matches `PROJECT.md`'s "no cross-user read path exists anywhere." | MED | RLS at the DB layer *and* query-scoping at the application/ORM layer — sources are consistent that relying on either alone is the common failure, not defense-in-depth. |
| Per-user encryption key, already decided | Per-tenant (here per-user) data keys are called the "gold standard" in multi-tenant encryption writeups — a compromise of one key exposes one user, not all. This is not new information; `PROJECT.md` already commits to per-user envelope encryption. Listed here only to confirm it matches external practice. | — | Already a settled decision. No new work implied. |
| Audit log on every privileged read | `PROJECT.md` already requires this. Confirmed as standard practice in every multi-tenant isolation source surveyed (immutable audit logs named alongside RLS and per-tenant keys as the three-part standard defense). | LOW-MED | Already scoped in PROJECT.md; no new finding, just corroboration. |

#### Export and portability

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Self-service, lossless data export (JSON/CSV) | General data-portability practice for any SaaS handling a user's own financial history: users should be able to take their data and leave, machine-readable, without asking an operator. Given the closed-group trust model there is no GDPR obligation, but the practice earns its place on its own — it is also the honest complement to "no cross-user read path": a user's *own* data must always be reachable by that user. | LOW-MED | Export raw fills, derived events (OPEN/CLOSE/ROLL/SETTLEMENT), campaigns, and the immutable entry records — the same objects the API already models. CSV for tabular consumption, JSON for full fidelity (nested campaign/roll structure does not flatten cleanly to CSV). |
| Export as a full account snapshot before deletion | Named practice in SaaS data-portability writeups: offer a final export before a deletion request is executed, so deletion is not also silent data loss. | LOW | One-time full export endpoint, triggerable from the deletion flow. |

#### API surface

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Resources grouped by aggregate, not by raw table | Financial-API convention: plural-noun resources (`/trades`, `/positions/{id}`, `/accounts/{id}`), not a 1:1 mirror of internal tables. `PROJECT.md`'s review surface requirements (campaign view with nested rolls, reconciliation status, drift) are themselves aggregate views, which argues for API resources shaped the same way: `/reconciliation`, `/campaigns`, `/campaigns/{id}` (rolls nested), `/connections`, `/connections/{id}/sync`. | MED | This is a naming/shaping decision more than new logic — the read models (campaign, reconciliation status, drift) are already specified in `PROJECT.md`; the API just has to expose them as first-class resources rather than making a client reconstruct them from raw fills. |
| Reconciliation status as its own endpoint, cheap to call | `PROJECT.md`: "queryable and is the first thing any client must render." Sync-status endpoint convention across the industry (Merge.dev and others) is exactly this shape: a lightweight status resource a client polls before rendering anything else. | LOW | `GET /reconciliation` (or per-user) returning green/red plus the failing window, distinct from the heavier campaign/event endpoints. |
| Manual re-sync trigger, idempotent | `PROJECT.md`: "Recompute is a pure function of stored fills, requiring no broker call" for recompute, but *ingest* (pulling new fills from Schwab) is a separate operation that a user must be able to force — e.g. after fixing a broker-side issue or a lapsed connection. Standard idempotency pattern: the broker's own fill/transaction id is the natural idempotency key, so re-running ingest for an overlapping window is a no-op past the first successful write, not a duplicate-fill bug. | MED | This is the multi-user-era version of the reconciliation invariant: re-sync must be safe to call repeatedly, by a human, without an operator watching. |
| Backfill of history at first connect | A new user connecting their Schwab account for the first time needs their existing open positions and recent history ingested, not just fills from the moment of connection forward. | MED | Distinct code path from the steady-state 30-minute ingest cycle — a bounded historical pull, same idempotency guarantee. |
| Sync result visibility ("what did the sync actually do") | Practitioner complaint pattern (both from the idempotency research and the trading-journal research's own §7 finding that "a journal that captures and cannot be queried fails") converges on: a sync that runs silently and produces no visible result is unauditable. | LOW | A sync-run record (started_at, completed_at, fills ingested, errors) queryable per connection — the mechanism that makes "did my re-sync work" answerable without reading server logs. |

### Differentiators (Competitive Advantage)

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Weekly re-auth reduced to near-zero friction | No comparable retail journal handles a 7-day-hard-expiry broker on top of a no-email closed group. Getting the pre-expiry-warning-plus-one-click-reconnect flow right (modeled on Plaid's `PENDING_DISCONNECT` pattern, adapted for a deterministic rather than probabilistic expiry) turns a structural weekly chore into a non-event. This directly serves the core value: if re-auth friction causes a user's connection to lapse, that user's ledger and snapshots go dark, and the reconciliation invariant cannot even evaluate for them. | MED | This is the single most differentiated multi-user feature in this research — no vendor surveyed operates against a hard 7-day server-enforced expiry, so no vendor's UX is a direct template; Plaid's scheduled-warning webhook is the closest structural analog, not a copy-paste pattern. |
| Per-user reconciliation status visible to the admin across all users | Single-user journals have no notion of "which of my users is dark right now." A closed group of 4-5 makes this cheap to build and valuable: the admin/owner can see at a glance whose connection needs attention, without any user's trading data being exposed to another user. | LOW-MED | This is an *isolation-respecting* aggregate — it shows connection health (a fact about the pipe, not about the trades), never P&L or positions across users. |

### Anti-Features (Commonly Requested, Often Problematic)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|------------------|-------------|
| Shared/social surface — group leaderboard, anonymized cross-user stats | Kinfo (broker-synced trading analytics with a community leaderboard) is a real precedent: sharing tiers from nothing to percentages-only to percentages+dollars, account size never shown, nickname not real name. It looks like a natural feature for a group of friends trading the same structure. | Two independent reasons to refuse, not one: (1) it requires a cross-user read path or a server-side aggregation step that decrypts multiple users' per-user-keyed data at once — `PROJECT.md` forbids any cross-user read path outright. (2) At n=4-5, a group average plus a user's own number is enough to back-solve the others' numbers algebraically — the small-group case defeats anonymization even before encryption is considered. Kinfo's own community reports its social layer "creates as many problems as it solves" even at retail scale with far more users. | None. If comparison is ever wanted, it is a manual, opt-in, out-of-band conversation between users — never a server-computed aggregate. |
| Role-based access control / org-team-workspace abstraction | Looks like standard SaaS scaffolding — most multi-tenant systems ship roles and permission tiers. | Solves a problem this project does not have: every user is a peer, every user owns exactly their own data, and there is one admin (the owner) who is also a user. Building a roles/permissions system for 4-5 fixed, known people is enterprise ceremony with no user to benefit from it. | A single `is_admin` boolean, if the admin needs any capability at all beyond a normal user (e.g. creating invites). No roles table, no permission matrix. |
| Email infrastructure (transactional email for invites, password reset, notifications) | Every SSPR and onboarding pattern surveyed assumes it; it is the default. | No email service exists in this project, and none is planned. Building around an assumed email channel means building a channel that will sit unused, or worse, quietly building the requirement for one later. | In-app notification/banner on login, plus the admin as the out-of-band channel for anything that would otherwise need email (invites, resets). |
| Self-serve public signup | Standard SaaS growth pattern. | There is no growth goal — the user set is fixed at 4-5 known people, decided by the owner, not by who discovers the product. A public signup endpoint is also an unnecessary attack surface for a system holding real brokerage credentials. | Admin-created accounts only (already listed as table stakes above). |
| Invite-link machinery with expiry/revocation/multi-use tracking | Reasonable at B2B SaaS scale where invites need to be tracked, expired, and audited across an organization. | At 4-5 known people, this is solving for an audience the product does not have — a single-use, admin-generated link with a fixed TTL is enough; anything more (invite dashboards, resend flows, bulk invites) is speculative scaffolding for a group that never grows. | One admin action per new user: generate a single-use setup link, hand it over out-of-band, done. |
| Admin impersonation / "view as user" tooling | Common support tool in multi-tenant SaaS, useful for debugging a specific user's issue. | Directly conflicts with `PROJECT.md`'s "no cross-user read path exists anywhere in the application" and the audit-log-on-every-privileged-read requirement — impersonation *is* a privileged cross-user read path, dressed up as a support feature. | If the owner genuinely needs to see a user's data for debugging, it goes through the same authenticated, audited path any privileged read does — never a shortcut. |
| Billing, plans, quotas, usage metering | Default SaaS scaffolding — most backend templates ship this. | No monetization exists or is planned; this is a private tool for the owner and a few friends. Building billing infrastructure with nothing to bill is pure speculative cost. | None. Skip entirely. |
| SSO / third-party auth (Google/GitHub login), MFA | Table stakes for a public-facing SaaS product. | Adds an entire external dependency and integration surface (OAuth provider config, account linking, MFA enrollment/recovery) for a product with 4-5 accounts the admin already provisions by hand. The security value MFA would add is better spent on the encryption and audit-log posture already required. | Username + password, admin-mediated recovery (already listed above). Revisit only if the user set or threat model changes. |
| Webhook subscriptions for third-party consumers | The API's own ingest-from-Schwab uses polling per `PROJECT.md`'s 30-minute cadence; it would be tempting to expose an equivalent webhook system outward, to the future UI client or other consumers. | No third-party consumer exists yet — the only planned client is the future first-party web UI, and `PROJECT.md`'s own sync-status pattern favors "client polls a cheap status endpoint" over "server pushes to arbitrary subscribers," matching the general finding that polling-as-source-of-truth with webhooks as an optional fast path (never webhook-only) is the safer default. | The reconciliation/sync-status endpoints already scoped as table stakes above; add a webhook only if and when a second, external consumer actually appears. |
| Tax-form-shaped export (e.g. an "8949 CSV") | Every other retail trading journal surveyed ships a tax-export feature, and it looks like an obvious differentiator for a journal handling real capital gains. | **Verified correction, not a stylistic choice:** SPX and SPXW are broad-based index options and IRC Section 1256 contracts. Section 1256 gains are marked-to-market, get automatic 60/40 long/short treatment regardless of holding period, and are reported on **Form 6781** feeding Schedule D — not Form 8949, which is for ordinary (non-1256) securities. Shipping an 8949-shaped export for this book's actual instruments would hand the user a wrong tax form. (MEDIUM confidence: consistent across four independent sources — terms.law, legalclarity.org, optionsdecay.com, cboe.com's own index-options tax page — but not verified against a real 1099-B or a CPA, and tax software/rules can change year to year.) | Ship raw, lossless portability export (already table stakes above) so the user or their CPA can compute the correct 1256/6781 treatment externally. If a tax-shaped export is ever built, it must target Form 6781's actual fields, not 8949's, and that decision needs a tax professional's sign-off, not a web search. |

## Feature Dependencies

```
Per-user Schwab OAuth connect
    └──requires──> Per-user envelope encryption key (already scoped in PROJECT.md)
    └──requires──> Connection health state (healthy/expiring/expired)
                       └──requires──> Pre-expiry warning threshold
                       └──enables───> Catch-up sync on re-auth
                                          └──requires──> Idempotent re-sync (broker fill id as key)

Admin-created accounts
    └──requires──> Admin-mediated password reset (same "no email" constraint)
    └──enables───> Per-account "stale for how long" visibility (admin-facing, isolation-respecting)

Self-service data export
    └──requires──> Same read models the API already exposes (campaigns, events, snapshots)
    └──enables───> Export-before-deletion step in account deletion flow

Row-level isolation + per-user key
    └──conflicts──> Any shared/social surface (leaderboard, group stats) — ANTI-FEATURE, not built
```

### Dependency Notes

- **Connection health requires per-user encryption**, because the connection health check itself
  reads (decrypts) a per-user stored token — it cannot be computed as a cross-user batch job without
  touching each user's data key individually. This bounds how "batched" any admin-facing "who is
  stale" view can be: it is N single-user checks, not one query.
- **Catch-up sync enhances re-auth**, not the reverse: re-auth can ship without an automatic
  catch-up trigger (the user could manually hit re-sync after reconnecting), but shipping catch-up
  without re-auth working first is meaningless.
- **Isolation conflicts with any shared surface.** This is the one hard conflict in the whole
  feature set: the leaderboard/social anti-feature is not merely undesirable, it is structurally
  incompatible with the per-user-key, no-cross-user-read architecture `PROJECT.md` already commits
  to. Any future push for a shared surface has to either accept a deliberate isolation exception (not
  recommended, not proposed here) or stay entirely client-side and out-of-band.

## MVP Definition

### Launch With (v1)

- [ ] Admin-created accounts, single-use setup link, admin-mediated password reset — the whole
  identity surface a closed group of 4-5 needs, nothing more
- [ ] Per-user Schwab OAuth connect, with connection health as a first-class field
      (healthy/expiring-soon/expired)
- [ ] Pre-expiry warning surfaced via API (client renders the banner) — the deterministic 7-day
  cycle is the single highest-friction recurring event in the system and must not degrade into
  silent data gaps
- [ ] Re-auth endpoint that repairs the existing connection record, never creates a duplicate
- [ ] Idempotent manual re-sync, keyed on the broker's own fill id
- [ ] Reconciliation status as its own lightweight, pollable endpoint
- [ ] Self-service full-account export (JSON, lossless) — this is also the deletion safety valve

### Add After Validation (v1.x)

- [ ] Automatic catch-up sync triggered on successful re-auth (v1 can require a manual re-sync
  click after reconnecting; automate once the manual path is proven correct)
- [ ] Admin-facing "who is stale, for how long" view across users
- [ ] Sync-run history/audit view (what a given sync actually ingested) beyond the minimum needed
  to debug reconciliation failures

### Future Consideration (v2+)

- [ ] Tax-shaped export — only after a tax professional confirms the correct form (Form 6781, per
  this research) and its exact required fields; not before
- [ ] Anything resembling a shared surface between users — deliberately deferred indefinitely, not
  merely sequenced later; see anti-features
