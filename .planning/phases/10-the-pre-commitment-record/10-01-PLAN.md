<objective>
Phase goal (ROADMAP, verbatim): "What the user said they would do is captured before the position
opens, and structurally cannot change afterwards."

This plan is the phase's tracer: the thinnest production-quality path through every layer the phase
touches. A logged-in trader submits one pre-commitment over HTTP; it is encrypted per-field under
their own data key, stored under row-level security, linked to a position once that position exists,
and frozen by a database trigger the instant an `OPEN` or `ROLL` event lands. Every layer — Alembic
migration, SQLAlchemy model, encrypted service module, Pydantic boundary, FastAPI route, app wiring
— is exercised end to end on one path before any expansion task widens it.

Purpose: criterion 2 is the phase's defining constraint, quoted here verbatim because it decides the
architecture — an update after the position opens must be "rejected structurally — by a constraint or
a trigger, not by a service-layer conditional a later caller could route around." A `CHECK`
constraint cannot see another table, so a `BEFORE UPDATE OR DELETE` trigger consulting `events` is
the only constraint-class mechanism that can express it (`D10-01`, `D10-02`). This is the first
`CREATE TRIGGER` this project has hand-written; the only other trigger DDL in the repo is
Procrastinate's own vendored schema in migration `0002`, which supplies the dialect.

Output: migration `0017`, the `EntryIntent` model, `src/morai/ledger/intent_tags.py`,
`src/morai/ledger/intent.py`, `src/morai/api/models_intent.py`, `src/morai/api/routes_intent.py`,
the router registration, and two new test files — one proving the round trip through the real HTTP
surface, one proving the freeze holds against a caller who never touches application code.

**On the ROADMAP goal line and MVP mode:** this phase is marked `**Mode:** mvp`, but its `**Goal:**`
line is outcome-shaped rather than in `As a / I want to / so that` user-story form. No story is
invented here — `/gsd mvp-phase 10` is the command that supplies one. The substantive half of MVP
mode, vertical slices instead of horizontal layers, is applied in full: this plan is one slice, and
after it a real user can do something they could not before.
</objective>

Research assumptions this plan acts on, named so a later reader sees them:

- **A1 — the position-id link is a separate, user-initiated API call, never automatic during
  ingest.** `create_positions` runs before `sync_events` inside one transaction
  (`src/morai/ingest/schwab_sync.py:471-472`), so nothing outside that transaction can observe or
  act in the window where a position exists with no `OPEN` event. The link is therefore necessarily
  a later call, issued once the caller has seen the new position id through the existing
  `GET /gate/positions` route. A task in this phase that edits `schwab_sync.py` is a signal to stop.
- **A2 — `REVOKE UPDATE` in `D10-02` resolves to a column-scoped grant on `position_id` and no
  table-wide `UPDATE` grant at all.** Postgres privileges are not row- or time-conditional, so a
  blanket revoke cannot both forbid every update and permit the one legitimate link. This is the
  only reading under which both halves of `D10-02` are true at once.
- **A3 — a migration importing application code has zero precedent here.** All sixteen existing
  migrations are self-contained. `D10-18` requires the vocabulary to live in exactly one place, and
  honouring it means the migration imports `morai.ledger.intent_tags`. The deviation is named
  rather than smoothed over, and Task 2's contract test is what makes it safe: widening an enum
  without a matching migration fails a test rather than passing silently.
