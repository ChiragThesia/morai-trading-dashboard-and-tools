<objective>
Phase goal (ROADMAP, verbatim): "What the user said they would do is captured before the position
opens, and structurally cannot change afterwards."

Plan 10-01 froze the pre-commitment. This plan closes the loop at the other end: when the position is
gone, the trader records whether they followed the plan and says in one sentence what happened, and
any closed position still missing that record announces itself inside the payload a client is already
reading.

Purpose: criterion 3 says "the close is not complete without it." Read literally that is a statement
about the *record*, not about the ledger. Blocking ingest on a user's note would let a trader on
holiday halt their own P&L; treating the note as optional would make the criterion vacuous. `D10-12`
takes the honest middle: the close is a complete fact and an incomplete record, and the system says
so out loud through the envelope Phase 9 already built.

Two asymmetries in this plan are deliberate and are stated rather than smoothed over. First,
`close_record` is mutable where `entry_intent` is frozen (`D10-14`) — a pre-commitment's whole value
is that it predates the outcome, and a retrospective note has no such property. Second, INTENT-07's
gate is service-layer where INTENT-06's is structural (`D10-17`) — `is_closed` is pure Python over
decrypted quantities and no Postgres trigger can decrypt. Nothing in this plan may imply criterion 3
is enforced by the database.

Output: migration `0018`, the `CloseRecord` model, `ExitReasonTag`, the close-record write and read
path, two new routes, the `close_note_outstanding` field on `PositionResponse`, and a test file that
pins the expiry limitation `D10-16` accepts.
</objective>

Decisions this plan acts on that a later reader should see stated:

- **`D10-16` is a scoping decision, not a claim that the gap is harmless.** It is the same failure
  shape as Phase 9's CR-01 blocker: work that is not failed and not indeterminate, just silently
  skipped. A front short put expiring worthless is a normal exit for these calendars, so at-close
  capture built on `is_closed` never fires for that whole class. This plan records the limitation in
  a test and a docstring and does not attempt the fix, which is phase-sized: `DerivedSettlement`
  carries only `(position_id, event_time)` and no leg id, so the fix must re-derive from expiry,
  which gives `derive_position_state` an `as_of` clock input and breaks the purity contract
  `tests/ledger/test_pairing_pure.py` gates, rippling to four call sites and Phase 8's open-leg set.
- **`close_record` must not be added to `tests/ledger/test_schema_contract.py`'s `_NEW_TABLES`.**
  That tuple's `test_grants_are_verb_narrowed` parametrisation asserts `UPDATE` is *absent* for every
  member, which is true of `entry_intent` and deliberately false of `close_record` (`D10-14`). This
  table gets its own RLS and grant assertions instead. Adding it to the shared tuple would produce a
  failing test whose correct fix is to remove it again.
- **The close note is encrypted although `10-CONTEXT.md` does not name that field explicitly.**
  `D10-09`'s stated reason — these are the free-text fields the security constraint was written for —
  applies identically to a one-sentence retrospective note. Recorded as an extension of a stated
  decision rather than the decision itself.

commit.
