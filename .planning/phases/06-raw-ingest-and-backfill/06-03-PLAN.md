<objective>
What a sync did, and a button that runs one. A `sync_runs` row records when a cycle ran, how much
landed and what errored; `last_synced_at` finally gets written, closing the loop Phase 4 opened; and
an authenticated user can trigger the same job the scheduler defers, repeatedly, safely.

Purpose: an ingest cycle that runs unattended is only trustworthy if a failure leaves evidence. The
hard part is not the table — it is that a failure record written inside the transaction that failed
rolls back with it, and the phase then reports a clean history for a broker connection that has been
dead for a week. That, and getting the web process the ability to enqueue a job without handing it a
superuser connection.

Output: migration 0012 and the sync-run record; classified error codes that never carry vendor text;
`last_synced_at` written on success only; the web process's deferral-only queue connection with the
grants it needs and nothing more; and the two routes, one to trigger and one to read.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vendor exception → stored record → HTTP response | The one path in this phase by which a token fragment or a full response body could reach durable storage and then a client. |
| web process → job queue | The web process gains the ability to enqueue work. What role it gains that ability as decides whether it also gains a way around every RLS policy. |

| failed transaction → failure record | If the record is written inside the transaction that failed, the system reports success by omission. |
