<objective>
Phase goal (ROADMAP, verbatim): "Open/closed state, per-leg settlement, and rolled-position chains
are computed from events, with no second writer for anything derivable."

This plan closes ROADMAP criterion 4's read half. It adds the thin Python wrapper over the
`campaign_chain` view migration 0014 created, and the two tests that make the view's two hardest
claims real: that dropping and recomputing the read model yields the identical chain, and that a
second user sees nothing of the first user's.

Purpose: LEDGER-10 forbids a separately maintained table. D7-11 chose a plain view over a
materialized one specifically so criterion 4's "dropping the campaign read model and recomputing it
from events yields the identical chain" is a runnable test rather than a metaphor.

The security stake is the highest in this phase. A `CREATE VIEW` applies the **view owner's** RLS
model by default, and the owner here is the migration's superuser, which carries `rolbypassrls`.
Without the invoker-rights clause every user querying the chain through `morai_app` reads every
other user's chain — silently, past a green single-user suite. `07-02` writes that clause; this plan
is where it is *proven*, by a real second-user query. A code read alone does not prove it works.

Output: `src/morai/ledger/campaigns.py` and `tests/ledger/test_campaigns.py`.
</objective>

Create `src/morai/ledger/campaigns.py`. Write `tests/ledger/test_campaigns.py` first — the natural red is a missing module, which costs nothing to observe. Do not build scaffolding to manufacture a more interesting failure.

Hold the query as a module-level named constant `READ_CAMPAIGN_CHAIN_SQL`, following `RESOLVE_FILL_POSITIONS_SQL`'s convention — raw SQL never lives inline in this codebase. Select `campaign_root_id`, `position_id` and `depth` from the `campaign_chain` view, ordered by `campaign_root_id` then `depth`, so two runs are comparable row-for-row. The chain-walking logic itself stays in the view; this module is a thin read wrapper and must not reimplement the recursion in Python.

Define a frozen dataclass `CampaignLink` with fields `campaign_root_id: UUID`, `position_id: UUID`, `depth: int`.

Define `read_campaign_chain(session: AsyncSession, user_id: UUID) -> list[CampaignLink]`. Narrow every column through a module-level `TypeAdapter` — the raw `text()` result types each column as `Any`, and this codebase resolves that with `TypeAdapter`, never `cast`. Bind `user_id` and add an explicit `WHERE` on it in addition to relying on RLS: the same both-belts discipline `read_fills` and `RESOLVE_FILL_POSITIONS_SQL` already use, where the query names its own scope rather than relying on the policy alone. Note in the docstring that the view carries the invoker-rights option, so the policy is what actually filters and the explicit clause is the second belt, not the first.

Define `read_campaign_for_position(session: AsyncSession, position_id: UUID) -> list[CampaignLink]`. Return every row sharing the `campaign_root_id` of the row whose `position_id` matches — the whole chain from any member, which is the direction a reader actually asks in (D7-10: the ROLL row hangs on the newly opened position, making the newest position the campaign head).

Record in the module docstring that this is a read model computed from events and nothing here stores a copy. D7-11 rejected a materialized view for exactly that reason: a second stored copy that can drift is the failure LEDGER-10 exists to prevent. Acquiring a stored copy later, for performance, is a decision that has to be taken explicitly.

Seed the test chains through `insert_events` with `rolled_from_position_id` set — the one write path. Do not insert `events` rows with raw SQL to sidestep the ROLL guards; those guards are part of what makes the chain trustworthy. A ROLL needs both money amounts, so supply real `Decimal` values in the fixtures and label the fixtures synthetic (D7-13).
