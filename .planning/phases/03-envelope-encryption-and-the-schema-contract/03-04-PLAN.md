<objective>
The data key's whole lifecycle: created with the account, re-wrapped when the master key
rotates without any trade row being touched, and destroyed before the rows it protects when
the account is deleted.

Purpose: criterion 3 and criterion 5 both hinge on ordering and blast radius rather than on
cryptography. Rotation is correct only if it provably does not touch trade ciphertext.
Deletion is a crypto-shred only if the key dies first — reversed, an interrupted deletion
leaves readable rows behind.

Output: `provision_data_key` wired into account creation, `rotate_kek` plus an operator
script, `delete_account` and the route that lets a user invoke it, and three test modules
proving each claim in the terms the validation contract names.
</objective>

      user, at `key_version` 1, with a non-null wrapped key and wrap nonce.
    - The wrapped key unwraps under the configured master key and yields 32 bytes.
    - The admin cannot read that row through the app role: with the admin's own RLS context

    **Name the trap before writing anything.** `user_data_keys` carries a `user_isolation`
    policy with a `WITH CHECK` on `app.current_user_id`, and `create_user` runs with the

    rejected by the policy. Do not solve this by adding an admin clause to the policy — that

    commit. Put a comment at the context switch naming why it is there and why the admin
    clause was not the answer, because the next reader's instinct will be the policy.

    rolls back both. A user without a key is an account whose first fill cannot be written,
    which is a worse state than no account.

    halves of `AUTH-06` sit in one place. Mark it `pytest.mark.db`.

  <name>Task 2: rotating the master key touches no trade ciphertext</name>
  <files>src/morai/crypto/rotation.py, tools/rotate_kek.py, tests/test_key_rotation.py</files>
  <read_first>
    `03-RESEARCH.md` Pattern 3 and Pattern 4 — `key_version` tracks the DEK, not the KEK, and
    a master-key rotation re-wraps the same DEK bytes rather than changing what the DEK is,
    which is the mechanism behind criterion 3's second half. `03-VALIDATION.md` criterion 3's
    trap: asserting only "it still decrypts" would pass even if every row had been rewritten.
    D3-07, CRYPT-04.
  </read_first>
  <behavior>
    - Seed two users, each with a data key and several fills and events carrying known
      `Decimal` values.
    - Record every trade-table ciphertext and nonce value as raw `bytes` before rotation.
    - Rotate from the current master key to a freshly generated second one.
    - Every recorded trade ciphertext and nonce value is byte-for-byte identical afterwards.
    - Every `user_data_keys` row's wrapped key and wrap nonce has changed.
    - Unwrapping under the new master key yields the same DEK bytes as unwrapping under the
      old one did before rotation.
    - Reading the fills and events back, with the new master key configured, returns the
      original `Decimal`s.
    - `key_version` on every trade row is unchanged, and no new `user_data_keys` row was
      added — a master-key rotation is not a data-key rotation.
    - Rotating with the wrong old key raises rather than writing anything.
  </behavior>
  <action>
    Write `src/morai/crypto/rotation.py` with one function taking a session, the old key bytes
    and the new key bytes. It selects every `user_data_keys` row, unwraps under the old key,
    re-wraps under the new one with a fresh wrap nonce, and writes both columns back. **No
    statement in this module may name a trade table.** That is what makes criterion 3's claim
    structurally true rather than true by accident, and it is the property the test asserts
    from the other side.

    Run the whole rotation in one transaction so a failure partway leaves every row wrapped
    under the old key rather than half under each. Unwrap-under-the-wrong-key must raise
    before anything is written; the transaction is what guarantees that.

    Neither key is persisted and neither is logged. Do not add a `kek_version` column: with
    exactly one live master key at a time and a single-invocation rotation, there is no
    concurrent multi-key window to track and the column would have no consumer. Note in the
    module docstring that this changes if the key ever moves to a KMS where more than one can
    be live, which is the revisit `D3-06` already records.

    `tools/rotate_kek.py` is the operator entry point: an `argparse` script taking the old and
    new keys as arguments or environment variables, running against the superuser engine
    (`get_engine`, not `get_app_engine`, since this is DDL-class maintenance and not a
    request), printing a count of rows re-wrapped and nothing else. It never prints or logs
    either key (`NN-34`). Model it on `tools/isolation_smoke.py`'s shape: a committed,
    runnable script with a docstring stating whether it has been run against a deployment,
    never a claim that it has.

    Write `tests/test_key_rotation.py` covering every bullet. The byte-identical assertion is
    the load-bearing one: capture the values into a dictionary keyed by primary key before
    rotation and compare the full dictionary afterwards, not a sample.

    Natural red: `ModuleNotFoundError` on `morai.crypto.rotation`.

    - Every read of the first user's fills and events now raises rather than returning a

      to one user.

    Write `src/morai/identity/account.py` with `delete_account(session, user_id)`. **The order
    is the claim, not an implementation detail.** Destroy the wrapped data key row first,
    then delete the trade rows, then the identity rows, then the user. Reversed or
    interleaved, an interrupted deletion leaves readable ciphertext behind with its key still
    present — the opposite of the guarantee. Put that reasoning in the function's docstring
    beside the ordering, so a later reader tidying the deletes into one statement per table in
    schema order knows why they must not.

    Make the read path fail loudly rather than quietly on a destroyed key: when
    `read_fills`/`read_events` find no `user_data_keys` row for a row's `key_version`, raise a

    absence of one is what makes deleting someone else's account unexpressible. Clear the
    session cookie the way `logout` does. Return 204.

    explicitly rather than only asserting the end state, because the end state alone would
    pass on a plain row delete that never touched the key.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| environment → rotation script | Both the old and the new master key arrive as parameters and are never persisted or logged. |
| admin session → a new user's data key | The admin creates the account but must not be able to read its key. |
| authenticated user → their own account deletion | The only account a session can destroy is its own. |
| a partially completed deletion → a later reader of the database | The window between key destruction and row deletion must already be safe. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-19 | Information Disclosure | Deletion that removes rows but leaves the key, or leaves rows after removing nothing | critical | mitigate | Key destroyed first, rows second, with the ordering asserted as an observable middle state rather than only an end state (ASVS 5.0 V14.1.1). |
| T-03-20 | Elevation of Privilege | One user deleting another user's account | critical | mitigate | `DELETE /me` takes no path parameter; the target is the session's own user id and nothing else can be named (ASVS 5.0 V8). |
| T-03-21 | Elevation of Privilege | An admin clause added to `user_data_keys` to make account creation work | critical | mitigate | Explicitly rejected; the route switches its transaction-local RLS context to the new user instead, following `/setup`'s precedent, with `require_rls_context` confirming it took (D2-08, D3-18). |
| T-03-22 | Tampering | A rotation that silently rewrites trade ciphertext | high | mitigate | No statement in the rotation module names a trade table, and the test compares every ciphertext and nonce byte before and after (ASVS 5.0 V11.1.1, documented key lifecycle). |
| T-03-23 | Information Disclosure | Either master key rendered in a log line, an error or the operator script's output | high | mitigate | The rotation script prints only a row count; neither key is logged, and configuration errors name fields only (`NN-34`). |
| T-03-24 | Denial of Service | A rotation interrupted partway, leaving keys wrapped under two different masters | medium | mitigate | The whole rotation runs in one transaction; a wrong old key raises before any write. |
| T-03-25 | Information Disclosure | A destroyed key making a read return empty rather than raising, hiding the shred | medium | mitigate | The read path raises a named missing-data-key error, so a crypto-shred is distinguishable from an empty account. |
</threat_model>
