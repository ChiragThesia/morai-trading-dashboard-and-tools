<objective>
Prove criterion 1 the only two ways that can actually fail on a leak: restore a real dump
into a scratch database with no master key present and compare raw bytes, and query the
stored nonces for a collision across every ciphertext column at once.

Purpose: this is the phase's headline security claim, and both of its obvious test shapes
are false-pass traps. A dump-file grep for a plaintext literal returns zero matches against
a column with no encryption whatsoever. A per-column nonce check misses a collision between
two columns of the same row, which is an equally real GCM break.

Output: two test modules that fail loudly against a broken implementation and cannot pass
against one.
</objective>

<task type="auto" tdd="true">
  <name>Task 2: no two ciphertext values share a key and a nonce</name>
  <files>tests/crypto/test_nonce_uniqueness.py</files>
  <read_first>
    `03-VALIDATION.md` criterion 1b and `03-RESEARCH.md` Pitfall 2, which gives the query
    shape: one `UNION ALL` branch per ciphertext column across every encrypted table, grouped
    by `(user_id, key_version, nonce)`, asserting no group has a count above one. Research
    tags the query itself as reasoned rather than executed, so run it for real here.
    Migrations 0007 and 0008 for the authoritative list of nonce columns.
  </read_first>
  <behavior>
    - Seed several hundred encrypted values across `fills` and `events` for two users through
      the real write paths.
    - The union query returns zero rows.
    - Planted collision: inserting two rows for one user under one `key_version` that share a
      nonce value, across two *different* columns, makes the query return exactly that group —
      so the query is proved capable of failing, not merely observed passing.
    - Schema drift guard: the set of `(table, nonce column)` pairs the query unions over is
      compared against the nonce columns actually present in `information_schema.columns`,
      and the test fails when a new ciphertext column has been added without a matching
      branch.
  </behavior>
  <action>
    Write the invariant query once, as a module-level constant, and use the same constant for
    both the clean assertion and the planted-collision assertion so the two cannot drift.
    Group by `(user_id, key_version, nonce)` — GCM's uniqueness requirement is scoped to the
    key and the nonce, so a nonce reused between a fill's price column and the same user's
    event amount column is as real a break as one reused within a single column, and a
    per-column check would miss it entirely.

    The planted collision goes in through the superuser session as raw SQL, deliberately
    bypassing the write path, because the write path is what makes a collision impossible and
    the point is to prove the detector works. Use two different columns for the planted pair,
    which is the case the naive per-column query cannot see.

    The drift guard is the part that keeps this test honest a year from now. Derive the list
    of nonce columns from `information_schema.columns` by name suffix, compare it to the
    literal list the query unions over, and fail with both sets in the message when they
    differ. Record in the module docstring that the current scale sits roughly 13,000x below
    NIST SP 800-38D §8.3's 2^32-invocations-per-key ceiling for random 96-bit nonces, so a
    counter-based nonce is not warranted and none is to be added.

    Natural red: the query names tables and columns that exist only after 0007 and 0008;
    running it before them is the red.
  </action>
