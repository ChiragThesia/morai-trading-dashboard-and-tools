<objective>
Turn CI from a report into a gate. A branch ruleset on `main` requiring a pull request and four
passing checks, proven by a pull request GitHub actually refuses and a pull request that merges
itself.

Purpose: criterion 2 says a branch introducing `Any`, a `cast`, or an unjustified suppression
"cannot be merged". Red CI reports; a ruleset refuses. This is the only option satisfying that
wording literally.

**The hazard this plan is sequenced around: a required status check that has never reported blocks
every pull request forever.** GitHub does not fail a pull request for a missing required check — it
waits, indefinitely, with no error explaining why. Create the ruleset before the workflow has run
once and every subsequent pull request, including every remaining phase of this milestone, hangs
unmergeable. That is a silent deadlock that looks like broken automation.

The order below is strict, not a suggestion. Plan 01-02 already did steps 1 and 2 — the workflow
exists and all four checks were observed reporting on a real commit. This plan does 3, 4 and 5.

Why last in the phase: creating the ruleset immediately stops direct pushes to `main`, and this run
is unattended.

Phase 1's own commits are already on `main`, and that is fine. This phase legitimately bootstraps the
gate it will then be governed by. Do not retroactively move its history onto a branch — that is churn
that rewrites published history for no benefit.

Availability is settled. Measured 2026-08-30: the repository is **public**, `repos/.../rulesets`
returns an empty array rather than a 403, and the account is on the free plan. GitHub gates rulesets
on repository visibility, not plan alone; public repos get them on every plan, and it is private
repos on Free that lose the feature. The phase context's `R-03` risk assumed a private repo and
evaporated on that fact. D-16 stands as written.
</objective>

do not treat the pull request as incidental.

catches a check-name mismatch. Task 1's character-for-character comparison is a static check; this is
the live one. Neither alone closes the loop. If a required context does not match a job name, proof A
still passes — the pull request is blocked either way — and every remaining phase of this milestone
