<objective>
Close the two real gaps in FastAPI's response validation, and prove they are closed with routes
that are supposed to fail.

Purpose: `response_model` already raises on a missing or wrongly-typed field. What it does silently
is drop extra fields and, outside strict mode, coerce — that is criterion 5's actual gap, per the
correction carried in D-09's own text. And a validation error is the code path most likely to have
a secret in scope, so what it returns to the client matters (`NN-34`).

Output: an opaque error envelope, a request id that ties it to a server-side log line, and a
negative-control router proving each failure raises rather than serialises.

Reversibility: D-11 is rated **costly** — declaring contracts by return annotation rather than the
`response_model` keyword is what gets two gates from one declaration, and switching back rewrites
every route signature and removes the adapters. Recorded, not gated.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: A request id, and an error body that structurally cannot leak</name>
  <files>src/morai/api/errors.py, src/morai/api/app.py</files>
  <behavior>
    - Every response carries a request id, generated once per request
    - A route raising `ResponseValidationError` produces a 500 whose body has exactly two keys: an error marker and the request id
    - The body contains no field name, no input value, no Pydantic message and no traceback
    - The server log holds one line for that failure carrying the full Pydantic detail and the same request id
    - An unhandled exception of any other type produces the same opaque 500 shape
    - A 422 raised by request validation keeps FastAPI's normal detail — a client sending bad input is entitled to know which field, and no server-side value is in scope on that path
  </behavior>
  <action>
Write the tests first and record the failing run (D-08).

`src/morai/api/errors.py`. A middleware that generates a request id with `uuid4().hex`, stores it
on `request.state`, and sets it as a response header. That is the id origin — a decision the phase
context left to the planner; a stdlib uuid needs no dependency and no coordination.

Two handlers, both returning `JSONResponse(status_code=500, content={"error": "internal",
"request_id": rid})` and nothing else: one for `fastapi.exceptions.ResponseValidationError`, one
catch-all for `Exception`. Each logs the full exception detail server-side at error level, keyed by
the same request id, before returning. D-10 rejected detail-in-dev-only precisely because it stands
one misconfigured environment variable away from leaking; an opaque body structurally cannot echo a
secret, and this is the path most likely to have one in scope.

Do not touch the 422 path. Request-validation detail names the client's own field and its own
submitted value; nothing server-side is in scope there, and suppressing it would make a strict API
undebuggable for the client that has to satisfy it.

Register the middleware and both handlers in `src/morai/api/app.py` at application construction.

Assert the log line in the test with pytest's `caplog`, matching on the request id from the
response body — that is what proves the detail went somewhere rather than nowhere. An opaque error
with no server-side record is worse than a leaky one.
  </action>

  </verify>

`tests/gate/routes_negative_control.py` holds an `APIRouter` of deliberately-broken routes, mounted
onto a throwaway FastAPI app inside the test rather than onto the real application. Each route
carries a one-line comment saying it is a negative control and must not be fixed. Nothing in
`src/` imports this file.

The strict-decimal cases are the exception in this directory: they assert success on the JSON
string form. RESEARCH.md names the precise warning sign — a fixture that posts D-03's own string
format to a money field and does **not** raise is the passing case, and if it raises, the
`BeforeValidator` protection has gone missing or been broken. The float and int cases assert
rejection, which is the protection strict mode was bought for.

Add the D-11 conformance check to the same test file: enumerate tracked files under
`src/morai/api/` with `git ls-files`, and assert none contains the response-model keyword argument.
Scope the scan to that directory only — never repository-wide — so plan prose and documentation
that legitimately name the keyword cannot invalidate it. FastAPI infers the response model from the
return annotation since 0.89, so one declaration gets two gates: basedpyright at build time and
FastAPI at runtime. The keyword is invisible to the type checker, which is why D-11 supersedes
STACK.md §2 on this point.

Excluding this router from the type checkers is not appropriate — these routes must themselves
type-check clean. Only their runtime behaviour is deliberately wrong, and that is the point: a
route that satisfies the type checker and still fails at the boundary is exactly the case
criterion 5 asks about.
