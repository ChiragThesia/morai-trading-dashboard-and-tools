<objective>
The second process. A Procrastinate worker on its own psycopg v3 pool, running one periodic
heartbeat, with Procrastinate's schema owned by Alembic like everything else.

Purpose: OPS-04 needs two processes against one database, and Railway needs a second service to
deploy. Two facts from research shape this and would otherwise be discovered the hard way.
Procrastinate ships no asyncpg connector — its five connectors are psycopg v3, aiopg, and three
sync defer-only variants — so the worker cannot share the web process's `AsyncEngine` pool and
must have its own. And Procrastinate documents no Alembic integration: its migrations are plain SQL
files meant for `psql`. Running `procrastinate schema --apply` as a separate deploy step would
create a second, untracked migration path — the same shape as the duplicated-write bug this project
avoids everywhere else. Wrapping the SQL in an Alembic revision keeps `alembic upgrade head` the
one command that brings any database to the right schema.

Output: a worker that boots, dequeues, and completes a job, on a schema Alembic owns.

Reversibility: D-13's migration chain is **one-way** — a deployed baseline is history. Recorded,
not gated, because the user asked for an unattended run.
</objective>

  <reversibility rating="one-way">A deployed migration chain is history. Phase 3 extends this chain rather than replacing it, and the revision ids here are permanent.</reversibility>
  <precondition>Postgres reachable at `DATABASE_URL` (`docker compose up -d`), and `alembic upgrade head` already applies the 01-02 baseline cleanly.</precondition>
  <files>alembic/versions/0002_procrastinate_schema.py</files>
  <action>
Locate Procrastinate's own SQL inside the installed package before writing anything. Run
`uv run python -c "import procrastinate, pathlib; p = pathlib.Path(procrastinate.__file__).parent /
'sql'; print(p); print(sorted(x.name for x in p.iterdir()))"` and read what is actually there.
Research established the shape — plain `.sql` files, applied with any Postgres client, a full
schema plus incremental `{version}_{seq}_{pre|post}_{description}.sql` migrations — but the exact
filenames for 3.9.0 were not enumerated. Read them; do not assume.

For a fresh database the correct baseline is the full current schema, not the incremental chain.
Take that file's contents verbatim into a single Alembic revision via `op.execute()`, chained to
the 01-02 baseline. Verbatim means verbatim: do not reformat, reorder, or "clean up" vendor SQL.

Write a real `downgrade()` that drops the objects the schema SQL creates — tables, types, and
functions — derived by reading that same SQL, not guessed. A revision whose downgrade lies is worse
than one that has none.

This is an application of a pattern research flagged as its own synthesis rather than
Procrastinate's documented recommendation. It is standard practice for wrapping any raw SQL into
Alembic, and the fallback if it misbehaves is the separate `procrastinate schema --apply` step —
which reopens the second-migration-path concern D-13 exists to avoid. Note in the revision's
docstring which Procrastinate version the SQL was taken from, so a future version bump knows what
it is superseding.
  </action>

  </verify>
  <done>A dropped-and-recreated database reaches head in one `alembic upgrade head`, including Procrastinate's tables; `downgrade -1` then `upgrade head` round-trips cleanly. `procrastinate schema --apply` appears nowhere in the repository.</done>

  <action>
Write the test first and record its failing run (D-08).

`src/morai/worker/app.py`: a module-level `procrastinate.App` whose connector is
`procrastinate.PsycopgConnector(conninfo=settings.sync_dsn)`. This is the one connector that is
both async and able to run a worker; `SQLAlchemyPsycopg2Connector` is sync and defer-only and does
not fit. Do not reach for an asyncpg connector — none exists. This pool is a separate budget line
against the Postgres connection ceiling from the web process's asyncpg pool (`NN-28`); cap it
explicitly rather than taking the library default, and say so in a comment.

One task, `heartbeat`, registered with `@app.periodic(cron=...)` and `@app.task(...)`. It logs its
run timestamp and returns. Nothing else — D-13's scope for this phase is one heartbeat task, and
the phase context is explicit that `gate_money_probe` is the only table Phase 1 creates, so the
heartbeat writes no table of its own. Its durable evidence is its own row in `procrastinate_jobs`.

Set the cron to fire every minute. This is Phase 1's heartbeat cadence and nothing else; the
30-minute RTH cadence is a system-wide fact that Phases 6 and 8 own, and the execution model behind
it is Phase 6's owned spike. Say that in a comment so nobody reads this cron as the project's
schedule.

The web process needs no Procrastinate connector at all in this phase — nothing defers a job from
a request. Do not add one. It becomes live the moment a later phase has the API enqueue work, and
that phase budgets the pool.

The test drives the real database, not `InMemoryConnector` — the point is to prove the psycopg pool
works. Defer the job, run the worker with a bounded stop condition, then query `procrastinate_jobs`
for the terminal status. Confirm the exact worker-running API against the installed package before
writing it: run `uv run python -c "import procrastinate; print([n for n in dir(procrastinate.App)
if 'worker' in n or 'run' in n])"` and use what is there. Bound the run so a hang fails the test
rather than hanging CI.
