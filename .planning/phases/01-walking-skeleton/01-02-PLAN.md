`src/morai/money/api_types.py` (R-02, measured): a module-level
`def _parse_decimal_strict(v: object) -> Decimal` returning `v` unchanged when it is already a
`Decimal`, returning `Decimal(v)` when it is a `str`, and raising `ValueError` naming the received
type otherwise — so a JSON float and a JSON int are both rejected. Export
`StrictDecimalField = Annotated[Decimal, BeforeValidator(_parse_decimal_strict)]` and a `UsdField`
alias for money in dollars. This exists because FastAPI routes every request body through
`TypeAdapter.validate_python` on a pre-parsed dict, never `validate_json` — read directly from
FastAPI 0.141.1's own source in RESEARCH.md R-02 — so a bare strict `Decimal` field would reject
the exact JSON-string format D-03 makes the API emit. Every money-carrying Pydantic field in this
project uses this alias, never a bare `Decimal`, `Usd` or `IndexPoints`. Function signatures and
non-Pydantic code keep using `Usd`/`IndexPoints` as D-01 specifies.

  <name>Task 2: The float canary — assert bit-inexactness, and say why it is not digit loss</name>
  <files>tests/test_decimal_canary.py</files>
  <behavior>
    - `Decimal(float(Decimal("9999999999.9999"))) != Decimal("9999999999.9999")` — the value cannot transit a float unaltered
    - The same holds for `Decimal("1234567890.1234")`
    - Both values fit `NUMERIC(14,4)`: at most 14 significant digits, at most 4 decimal places
    - A control assertion documents that `Decimal("7425.5000")` IS bit-exact as a double, so a future reader cannot swap it in and silently stop testing anything
  </behavior>
  <action>
Write the test first and observe it fail (D-08) — start with a deliberately wrong expectation, or
with the assertion helper absent, so the red run is real.

Assert **bit-inexactness**, `Decimal(float(x)) != Decimal(x)`. Do not assert a visible digit flip.
RESEARCH.md measured this across 8 candidates and the orchestrator reproduced it independently:
`NUMERIC(14,4)` holds at most 14 significant digits, an IEEE-754 double carries about 15.95, so no
value both fits the column and visibly loses a digit at four decimal places. A test claiming
otherwise would be dishonest and unprovable at this column width.

Put that reasoning in the test module's docstring and in the assertion messages, in one or two
sentences, so a future reader hunting for a value that "actually looks different when printed"
finds the answer instead of the hunt. State plainly that none exists inside this column's range.

Include `Decimal("7425.5000")` as an explicitly-labelled counter-example asserting it IS bit-exact
— it is an exact binary fraction, and using it as the canary would pass for the wrong reason.

What the canary buys: it proves that if the pipeline had put a `float` anywhere on the money path,
the value would provably differ. The route's own design — `Decimal` end to end, asyncpg's native
`NUMERIC ↔ Decimal` binding, D-03's string JSON — is what prevents that; the canary is what proves
the prevention is doing work rather than the value being float-safe by luck.
  </action>
