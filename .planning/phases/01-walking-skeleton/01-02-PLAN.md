<objective>
Continuous integration, built before anything that needs a database — because on this machine CI is
the only place a database-backed test can run at all.

Purpose: Docker's daemon is broken here and Railway's Postgres is private-network-only, so the
GitHub Actions `services: postgres` container is the project's working test database. Every later
plan's DB-backed verification routes through this workflow. It also lands criterion 3's first half:
the suite runs on every push.

Output: a workflow whose four job names are the exact strings the ruleset in plan 01-10 will mark
required, **observed reporting on a real commit**.

Why this precedes the tracer: the tracer's whole point is a real round trip through real Postgres.
Without this workflow there is nowhere to run it. Tracer-first ordering yields here to a physical
constraint, not to preference.

Note on job shape: GitHub Actions is free and unmetered on public repositories. There is no minutes
budget to design around. Do not consolidate the four checks into one job — separate names give
precise failure attribution and are what the ruleset references by string.
</objective>

<task type="auto">
  <name>Task 1: Four named jobs, a Postgres service container, and proof all four report</name>
  <files>.github/workflows/ci.yml</files>
  <action>
Write `.github/workflows/ci.yml`. Trigger on `push` and on `pull_request` targeting `main`.
Declare read-only `permissions` at the workflow level rather than inheriting the repository default;
no job here needs a secret or a write scope.

Four jobs, named **exactly**:

    typecheck-basedpyright
    typecheck-mypy
    lint-ruff
    test-pytest

Record those four strings verbatim in this plan's summary. Plan 01-10 marks these exact contexts
required, and a mismatch there does not error — GitHub waits forever for a check that never
arrives, which reads as pending. A typo becomes a silent permanent block on every future pull
request.

Every job: checkout, install `uv` via `astral-sh/setup-uv`, then `uv sync --frozen`. Let `uv` read
`.python-version` rather than hardcoding a version in the workflow — one pin, one place.

Each job runs the same command `tools/gate.sh` runs for that tool. The `test-pytest` job
additionally declares a `services: postgres` container on `postgres:18-alpine` — the same major
`docker-compose.yml` pins, which is the major the live Railway Postgres runs — with a `pg_isready`
health check, sets `DATABASE_URL` to that container, and runs `uv run alembic upgrade head` before
`uv run pytest`. At this point the revision chain is empty, so the upgrade is a no-op that proves
the Alembic import path and the database connection rather than a schema. That is exactly what
should be proven first.

Run the full `pytest`, including `db`-marked tests. CI is where they belong.

Do not add caching, a matrix, or a coverage upload. None is asked for, and each is a thing that
breaks later for reasons unrelated to the code.

Then push and **observe all four checks actually report on a real commit**. Do not proceed on "the
file exists". Capture the `gh run list` output and the run URL for the summary — plan 01-10's
ruleset is authorised by this observation, not by the workflow's existence.
  </action>
