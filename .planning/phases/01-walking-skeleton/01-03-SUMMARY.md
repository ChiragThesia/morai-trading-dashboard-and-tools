## Decisions Made

- **Canary literals and assertion form:** `Decimal("9999999999.9999")` (the `NUMERIC(14,4)` ceiling) and `Decimal("1234567890.1234")` (CONTEXT.md's mid-range example), both asserted `Decimal(float(x)) != x` -- bit-inexactness, not a visible digit flip, per R-01's measured finding that no value fitting this column width can visibly lose a digit through a float. `Decimal("7425.5000")` is the labelled negative control, asserting `==` (it's an exact binary fraction).
- **`StrictDecimalField`:** `Annotated[Decimal, BeforeValidator(_parse_decimal_strict)]`, accepting `Decimal` or `str`, raising `ValueError` (naming the received type) for anything else -- confirmed against the live `MoneyRoundtripRequest` model (see Verification below), matching R-02's measured table exactly.
- **Alembic baseline hand-written**, matching `GateMoneyProbe` field-for-field, since no local database exists to run `--autogenerate` against.
- **Session-scoped test event loop** (see Deviations) -- not in the plan's text, but required to make the app's own `lru_cache`d `AsyncEngine` usable across more than one test in a suite where pytest-asyncio otherwise hands out a fresh loop per test function.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `lru_cache`d `AsyncEngine` failed on the second parametrized test with "attached to a different loop"**

- **Found during:** Task 2, the CI run for the `feat` (GREEN) commit ([33340261536](https://github.com/ChiragThesia/morai-trading-dashboard-and-tools/actions/runs/33340261536))
- **Issue:** `morai.db.session.get_engine()` is `lru_cache`d (correct for production: one process, one event loop, one connection pool for its whole life). pytest-asyncio's default event-loop scope is per test *function*, so the first parametrized case built the asyncpg pool inside that test's loop, and the second parametrized case's different loop then tried to use it: `RuntimeError: Task ... got Future ... attached to a different loop`.
- **Fix:** `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in `pyproject.toml`'s `[tool.pytest.ini_options]`, so the whole test session shares one event loop -- matching the single-process, single-loop assumption the cached engine is actually built on. Rejected: dropping the `lru_cache` (defeats connection pooling in production for a test-only problem) and rebuilding the engine per request (a real production performance regression).
- **Files modified:** `pyproject.toml`
- **Verification:** CI run [33340338624](https://github.com/ChiragThesia/morai-trading-dashboard-and-tools/actions/runs/33340338624) -- `test-pytest` `16 passed in 0.64s`, all four jobs green.
- **Committed in:** `01a5489` (separate `fix:` commit)
