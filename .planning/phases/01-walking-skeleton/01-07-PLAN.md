  <name>Task 1: Four named jobs, one Postgres, one pinned interpreter</name>
  <files>.github/workflows/ci.yml</files>
  <action>
Write `.github/workflows/ci.yml`. Trigger on `push` and on `pull_request` targeting `main`.

Four jobs, named exactly `basedpyright`, `mypy`, `ruff` and `pytest`. Record those four strings in
the plan summary — plan 01-10 marks these exact names as required checks, and a mismatch there
silently gates nothing.

Every job: checkout, install `uv` via `astral-sh/setup-uv`, then `uv sync --frozen`. Let `uv` read
`.python-version` rather than hardcoding a version in the workflow — one pin, one place. Do not
call `actions/setup-python` with a literal version; that is the drift D-17 avoids for Postgres,
applied to the interpreter.

Each job runs the same command `tools/gate.sh` runs for that tool, so CI and any local hook cannot
diverge. The `pytest` job additionally declares a `services: postgres` container on
`postgres:18-alpine` — the same major version `docker-compose.yml` pins, which is the same major
the live Railway Postgres runs — with a `pg_isready` health check, and sets `DATABASE_URL` to that
container. Run `uv run alembic upgrade head` before `uv run pytest`, exactly as a developer does
locally.

Do not add a caching step, a matrix, or a coverage upload. None is asked for, and each is a thing
that breaks later for reasons unrelated to the code.

No secret is needed by any job. If one ever is, it comes from GitHub Actions secrets, never from a
committed file — the repository is public.
  </action>

  </verify>
