<objective>
The second process. A Procrastinate worker on its own psycopg v3 pool, running one periodic
heartbeat, with Procrastinate's schema owned by Alembic like everything else.

Purpose: OPS-04 needs two processes against one database, Railway needs a second service to deploy,
and plan 01-08's criterion 1 measurement needs a second service to originate a request from inside
Railway's private network. The worker is load-bearing for all three.

Two research facts shape this and would otherwise be discovered the hard way. Procrastinate ships no
asyncpg connector — its five are psycopg v3, aiopg, and three sync defer-only variants — so the
worker cannot share the web process's `AsyncEngine` pool. And Procrastinate documents no Alembic
integration: its migrations are plain SQL meant for `psql`. Running `procrastinate schema --apply`
as a deploy step would create a second, untracked migration path, the same shape as the
duplicated-write bug this project avoids everywhere.

**Verification runs in CI.** There is no local database — Docker's daemon is broken here and
Railway's Postgres is private-network-only. Mark this plan's DB-backed test `@pytest.mark.db` and
prove it on the `test-pytest` job from plan 01-02.

Reversibility: D-13's migration chain is **one-way** — a deployed baseline is history. Recorded, not
gated, because the run is unattended.
</objective>

  <files>alembic/versions/0002_procrastinate_schema.py</files>
  <action>
Locate Procrastinate's own SQL inside the installed package before writing anything — this needs no
database and runs here. `uv run python -c "import procrastinate, pathlib; p =
pathlib.Path(procrastinate.__file__).parent / 'sql'; print(p); print(sorted(x.name for x in
p.iterdir()))"`. Research established the shape — plain `.sql` files applied with any Postgres
client, a full schema plus incremental `{version}_{seq}_{pre|post}_{description}.sql` migrations —
but the exact filenames for 3.9.0 were not enumerated. Read them; do not assume.

For a fresh database the correct baseline is the full current schema, not the incremental chain.
Take that file's contents verbatim into a single Alembic revision via `op.execute()`, chained to the
01-03 baseline. Verbatim means verbatim: do not reformat, reorder, or clean up vendor SQL.

Write a real `downgrade()` dropping the objects the schema SQL creates — tables, types, functions —
derived by reading that same SQL, not guessed. A revision whose downgrade lies is worse than one
that has none.

Note in the revision's docstring which Procrastinate version the SQL came from, so a future version
bump knows what it supersedes.

This applies a pattern research flagged as its own synthesis rather than Procrastinate's documented
recommendation. It is standard practice for wrapping raw SQL into Alembic, and the fallback if it
misbehaves is the separate `procrastinate schema --apply` step — which reopens the
second-migration-path concern D-13 exists to avoid.

Verification is CI, not local. Push and read the `test-pytest` job, which runs `alembic upgrade
head` on a clean Postgres service container every run — that container is created fresh per job, so
every CI run is already the drop-and-recreate test.
