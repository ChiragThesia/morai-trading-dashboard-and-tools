  <action>
Author `.railway/railway.ts`, not `railway.toml` and not `railway.json`. Railway's config-as-code
is deprecated and **new services cannot opt into it at all** — fetched from Railway's own docs on
2026-08-30. Both services here are new. This is also why the existing `.claude/CLAUDE.md` and the
pre-roadmap `research/STACK.md` cannot be followed literally on this point: both predate the
deprecation.

Re-fetch `https://docs.railway.com/infrastructure-as-code/reference.md` before writing the file.
Research dated its Railway findings valid for seven days precisely because the platform is
mid-migration. Write against what the reference says today, not against the shape quoted in
RESEARCH.md.

The shape, adapted from the reference's own web-plus-worker-plus-Postgres example:

  - the existing Postgres, referenced rather than provisioned — this project already has one, and
    the sample's `postgres("postgres")` helper provisions a new one
  - a `web` service: source is this GitHub repository at `rootDirectory: "."`, healthcheck `/health`,
    `DATABASE_URL` referenced from the Postgres service's own typed accessor
  - a `worker` service: same source, same `rootDirectory`, same `DATABASE_URL`, no healthcheck

Both services point at the repository root and differ only in their start command — this is one
installable package with two entry points (D-18), not a monorepo, so the reference's distinct
`rootDirectory` values do not apply. Research flagged this as an assumption; confirm it on the
first deploy.

Web start command: `hypercorn --bind '[::]:$PORT' morai.api.app:app`. The explicit dual-stack bind
is `V039`'s prescription, it costs nothing, and it covers both possible answers to the spike in
task 2. Railway injects `PORT` and checks the same port. Uvicorn stays a local-development
dependency only.

Worker start command: `procrastinate --app morai.worker.app.app worker`.

Migrations run before the web process serves. Prefer a Railway pre-deploy command if the IaC
reference documents one for `service()`; read the reference and use it if it is there. If it is
not, chain it into the web service's start command as `alembic upgrade head && hypercorn ...`.
Only the web service runs migrations — two services racing the same `alembic upgrade` is a
deadlock waiting for its first slow migration.

Builder is nixpacks, Railway's default. No Dockerfile (D-19). Consequence to carry into task 3:
Railway owns the base image and the Python patch version, so `V092` must record both alongside the
bind result. Without that, the next drift in Railway's builder is undetectable — the same class of
problem that left `V039` flagged partially stale.

No secret in this file. It is committed, and the repository is public. `DATABASE_URL` is a service
reference; the live Postgres password is readable from `railway variables` at any time and must
never be written into a committed file. Update `.env.example` with the deployed callback shape if
anything changed, placeholders only.

Deploy both services. Then confirm the Postgres major version the code was built against:
`SELECT version()` through the deployed service or `railway run`. It read
`ghcr.io/railwayapp-templates/postgres-ssl:18` on 2026-08-30, which is why `docker-compose.yml` and
the CI service container both pin major 18. If the live database reports a different major, correct
both pins in the same commit as this task (D-17).
