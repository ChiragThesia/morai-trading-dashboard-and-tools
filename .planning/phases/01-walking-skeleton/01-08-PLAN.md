This is the phase's owned spike, and its answer is already known from independent measurement — the
job here is to reproduce it against this deployment and record the raw output. Keep this evidence in
its own section, separate from task 1's criterion 4 evidence.

**The mechanism, re-measured across three resolvers before this plan was written:** Railway's public
edge is IPv4-only. `healthcheck.railway.app` returns no AAAA record from the system resolver, from
8.8.8.8, or from 1.1.1.1 — only `A 34.107.141.139`. Railway's private network
(`*.railway.internal`) is IPv6. One `[::]` dual-stack bind serves both on one socket. That is V039.

**The trap:** `railway.app` itself DOES return AAAA (`2606:4700::/32` — Cloudflare, fronting
Railway's marketing website). Those are not the edge that serves deployed applications. If a probe
digs `railway.app` it will produce a confident wrong answer. Target the generated `*.up.railway.app`
domain, and `healthcheck.railway.app`, and nothing else.

Three probes. Record the **verbatim** output of each — HTTP code or the exact connection error. Do
not summarise and do not stop early.

  1. **IPv4 half — the real probe.**
     `curl -4 -sS -o /dev/null -w '%{http_code}\n' https://<web>.up.railway.app/health`
     Expect `200`. This proves the public edge reaches the `[::]` bind over IPv4.

  2. **Expected-failure control — NOT a probe.**
     `curl -6 -sS -o /dev/null -w '%{http_code}\n' https://<web>.up.railway.app/health`
     This **will** fail to resolve or connect, because Railway's public edge has no AAAA record.
     **Its failure is the expected result and confirms the finding.** It is not a phase failure, it
     is not a bug, and it must not be "fixed".
     **Explicit warning to the executor: do NOT respond to this failure by removing or changing the
     `[::]` bind in `.railway/railway.ts`.** That bind is this phase's actual deliverable. The
     failure here is a property of Railway's edge, not of this service. Capture the error text and
     move on.

  3. **IPv6 half — the real probe.**
     From the worker service:
     `railway run --service worker -- curl -sS -o /dev/null -w '%{http_code}\n' http://<web>.railway.internal:$PORT/health`
     Expect `200`. This is the private-network path, and it is the half of V039 that was ever
     actually about dual-stack binding. It requires the worker, which is why this task depends on
     both deployments.

Then capture the two facts D-19 requires: the exact Python version and the exact base image nixpacks
produced. Both are named in the deployment build log (`railway logs --build` or the deployment
detail). Record them verbatim. Without them the next drift in Railway's builder is undetectable,
which is the same class of problem that left V039 flagged partially stale in the first place.

**Verdict: V039 re-measured and CONFIRMED, not refuted.** The mechanism holds and the dual-stack
bind is still required. Record it that way.
  </action>
