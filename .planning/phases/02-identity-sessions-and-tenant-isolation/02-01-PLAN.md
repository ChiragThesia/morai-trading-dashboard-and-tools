Purpose: D2-09 deferred the isolation mechanism to research, which returned a single

now that the spike has shown there is no pooler in front of Railway's Postgres.
`02-RESEARCH.md`'s central finding is that Railway's `postgres` role is (inferred to be) a
superuser, and a superuser ignores RLS entirely — `FORCE ROW LEVEL SECURITY` does not
change that. An app that runs its queries as that role has policies
that are silently inert, and a naive isolation test would still pass, because the
application's own `WHERE user_id = ...` masks the fact that the policy never fired. So
the role comes first, before any policy is worth writing.

## What this phase inherited, and what is deliberately not being changed

Read before touching anything. Phase 1's decisions are load-bearing here.

- **`get_settings()` is `lru_cache`d, not a module singleton.** Do not add a module-level
  `settings = ...`. It fails at import, not at boot, which is a different and worse thing.
- **Route contracts are return type annotations, never `response_model=`.**
  `tests/gate/test_api_boundary.py::test_no_route_under_src_morai_api_declares_response_model`
  parses `src/morai/api/` with `ast` and will catch a violation.
- **Every request and response model derives from `ApiModel`** (`strict=True`,
  `extra="forbid"`, `frozen=True`).
- **`NN-34` outranks everything in this plan.** No password, no password hash, no session
  token, no setup nonce, no DSN password goes into a log line, an exception message, an
  error body, a test fixture name, or a commit message. `settings.load_settings` already
  keeps values out of boot errors with the `raise` outside the `except`;
  `api/errors._ErrorLocation` already drops pydantic's `input` key structurally;
  `telemetry.capture_exception` already never sends `str(exc)`. This phase introduces the
  first secrets those three defences actually exist for. Do not weaken any of them.
- **There is no local database.** Docker's daemon is broken and Railway's Postgres is
  private-network-only. `uv run pytest -m "not db"` is the local default; every `db`-marked
  test is proven in CI's `services: postgres` container.

## The correction that reshapes the CI story

`02-RESEARCH.md` was amended (commit `128d7a2`) to separate two claims that had been
merged:

- The **rule** — superusers and `BYPASSRLS` roles always bypass row security, and `FORCE
  ROW LEVEL SECURITY` binds only the table *owner* — is quoted directly from official
  Postgres documentation. Solid.
- The **status** of the live `postgres` role on this specific Railway instance was never
  queried. It is a two-step inference. The one-line check that settles it is
  `SELECT rolsuper FROM pg_roles WHERE rolname = current_user;`.

CI has the identical problem and it is the half most likely to be missed. CI's service
container runs as `postgresql://morai:morai@localhost:5432/morai`, and in the official
Postgres image the `POSTGRES_USER` is itself the bootstrap superuser. **A CI isolation
test that connects as `morai` has RLS inert for exactly the same reason production would,
and passes while proving nothing.** So CI creates and connects as its own non-superuser
role — the same `morai_app` the migration creates on Railway. This is why the role is a
Task 2 deliverable and not a hardening step bolted on at the end.

## Decisions this plan makes, with their reasons

- **One new secret, not two.** `MORAI_APP_DB_PASSWORD` only. `Settings.app_async_dsn`
  composes the runtime DSN from `database_url`'s already-correct host and database name
  with the new role and password, via SQLAlchemy's own `make_url(...).set(...)`. A second
  full `APP_DATABASE_URL` variable would duplicate the host and database name in a second
  place that can drift, and the migration would still need the password separately —
  two variables, one of which can silently disagree with the other.
- **`get_db_session` switches wholesale to the app role.** Not a second parallel
  dependency. A superuser-capable session sitting in the web process is precisely the
  backdoor RLS exists to close, and "which session did this route use" is not a question
  anyone should have to ask. The consequence is that `gate_money_probe` and its sequence
  need explicit grants — included in the migration, and `tests/test_money_roundtrip.py`
  proves it.
- **UUID primary keys on every new table.** Phase 3's envelope encryption keys a per-user
  data key by whatever identifies a user here (`02-CONTEXT.md` `<specifics>`), so the
  identifier's shape outlives this phase. UUIDs also mean no sequences to grant.
- **`sessions` and `setup_tokens` carry no RLS policy, deliberately.** Possession of the
  opaque 256-bit token *is* the authorization, and both are read by a request that has no
  RLS context yet — the session lookup is the very thing that establishes it. Written into
  the migration as a comment, so a later reader does not read the absence as an oversight.
- **`audit_log` gets RLS with an INSERT-only policy and no SELECT policy.** Nothing in
  phase 2 reads it, and append-only-from-the-app is free to have and expensive to retrofit.
- **`users` carries an admin clause; no table holding user-owned data ever does.** This is
  `02-RESEARCH.md` Pitfall 4, and it is written into the migration as a comment next to the
  policy so the next person copying a policy as a template sees the distinction before they
  copy the wrong one.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → FastAPI route | The session cookie is untrusted input. An attacker supplies arbitrary bytes. |
| FastAPI process → Postgres | The app role's own privileges are the last enforcement layer. Above this line is discipline; below it is the query planner. |
| Alembic (superuser) → Postgres | DDL runs with full privilege. Anything the migration gets wrong is unguarded. |
| operator → Railway variable store | `MORAI_APP_DB_PASSWORD` transits a human's hands once. |
