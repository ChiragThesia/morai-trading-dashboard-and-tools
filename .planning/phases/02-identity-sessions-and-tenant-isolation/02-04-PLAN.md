## The honest ceiling, stated before the code is written

D2-11 asks for the strongest rung achievable and for a straight answer about which one it
is. Here is the answer, and the plan text must carry it — no task in this plan may claim
the audit log "cannot be bypassed", because that is not what is true.

**What type-checks (a real "does not compile"):** `get_user_for_management(session, proof:
AuditedRead)` has exactly one signature. A caller who reaches for the obvious thing —
`get_user_for_management(session, subject_id)` — passes a `UUID` where an `AuditedRead` is
required, and both basedpyright and mypy reject it. This is the same class of guarantee as
`needs_usd(IndexPoints(...))` in `violation_unit_confusion.py`, and it is provable with
the identical subprocess mechanism already in `tests/gate/test_type_gate.py`.

**What does not type-check (falls back to a runtime guard):** a caller who *forges* an
`AuditedRead` by constructing one directly with some other sentinel gets a `RuntimeError`,
not a type error. Type checkers verify shapes, not provenance. This is tested as a unit
test and labelled a runtime guard.

**What neither covers:** whether a reviewer notices that a brand-new privileged surface
should route through this pattern at all. That is D2-11's own explicit fallback rung
("beats a review convention"). The pattern reduces how much rests on review; it does not
remove review.

Write those three paragraphs into `audit.py`'s module docstring. A future reader who finds
this file and concludes it is airtight will build the fourth thing on top of a guarantee
that was never made.

## Where the audited read path actually applies, and where it must not

There is exactly one legitimate cross-user read in this system: admin account management —
looking up user B's row to issue a setup link or reset a password (AUTH-01, AUTH-05).

Trading data has **no** legitimate cross-user read, including for the admin (D2-08). It
never gets an `AuditedRead` path. Only RLS. `02-RESEARCH.md` Pitfall 4 is the trap: the
`users` policy's admin clause is not a template, and a future data table that inherits it
makes Phase 3's whole encryption boundary decorative. Say this in the docstring next to the
capability, where someone about to add a second audited surface will read it.

## D2-12 — one transaction, or the audit is worse than nothing

The audit row is written on the same `AsyncSession` as the read, and `open_audited_read`
does **not** commit. The caller's single commit covers both; a rollback drops both. A read
that succeeds while its audit row is lost is worse than no audit log, because it looks like
coverage.

`audit_log` carries an INSERT-only RLS policy and no SELECT policy (plan 02-01's
migration), so the app role can append and cannot read or alter its own trail.
