## Cookie attributes: which world, and what changes in the other one

D2-07 asked research to state which world we are in and what changes if it is the other.
Research answered, and the answer is a default with a stated cost of being wrong, not a
fact:

**World A — the UI ends up same-site with the API** (`app.example` and `api.example`
sharing a registrable domain). `SameSite=Lax` is correct and sufficient. No CORS credential
dance, no separate CSRF defence. **Build this.** It is the recommended target and the more
likely shape for a solo-plus-friends project.

**World B — the UI ends up on a genuinely different registrable domain** (a Vercel domain
calling a `railway.app` API). `SameSite=Lax` cookies are silently **not sent** on
cross-site `fetch`/XHR. This is `02-RESEARCH.md` Pitfall 5, and its failure signature is
"works when I test it by hand, fails from the deployed frontend" — because top-level
navigations always send `Lax` cookies and a `fetch` does not.

Exactly what changes, so this is a config change and not a redesign:
1. `samesite="lax"` becomes `samesite="none"`, which Starlette requires pairing with
   `secure=True` — browsers reject `SameSite=None` without it.
2. CORS with an explicit origin, never `*`, plus `Access-Control-Allow-Credentials: true`.
3. A real CSRF defence — a double-submit token. `SameSite` *was* the CSRF mitigation in
   World A, and it is gone in World B.

World B's requirements are a strict superset of World A's, not a contradiction, so guessing
wrong costs bounded rework and not a silent security gap. Put those three numbered items in
a comment beside the `set_cookie` call. The person who hits this will be debugging a cookie
that is not being sent, and they should find the answer at the call site.

## Session lifetime

D2-06: persistent cookie with an explicit `max_age`, 30 days, so a browser restart keeps
the session. Sliding renewal is deferred — every renewal path is another place a revoked
session can be resurrected, and it is a comfort feature.

## The one thing a login route can leak by accident

An unknown username that returns without hashing anything answers in a fraction of the
time a real username with a wrong password takes, because the real path pays 250-400 ms of
Argon2. That difference is measurable and it is a username oracle. Hash against a dummy
hash on the unknown-username path so both branches pay the same cost. This is cheap and
it is the standard control; do not skip it because the user count is small.

## What this session could not do, and why the phase does not depend on it

Four things:
1. Set `MORAI_APP_DB_PASSWORD` on Railway. Blocked by the permission classifier, same as
   `railway config apply` was in Phase 1.
2. Deploy, and therefore measure Argon2id on the real container (D2-03).
3. Run `tools/isolation_smoke.py` against the live service (D2-10).
4. Create the first admin on the deployed database.

None of them gate anything in this phase. Everything is proven in CI, where the executor
creates and connects as `morai_app` itself — which is a *stronger* proof than a smoke test
against the deployment would be, because both roles are under the test's control and the
negative case can be asserted. `.claude/rules/workflow.md` is binding here: when you cannot
verify something, say so explicitly rather than softening the claim. The runbook says these
have not been done.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client → `POST /login` | Username and password from an untrusted caller. |
| browser cookie jar → every authenticated route | The session cookie is the only credential on every subsequent request. |
| future UI origin → API origin | Undecided today. `SameSite` is the control, and which value is correct depends on a decision nobody has made yet. |

| T-02-35 | Spoofing | A session cookie replayed after logout | critical | mitigate | Logout deletes the row. The test asserts the absence and the 401 in one function, so a client-side-only logout fails (D2-05). |
