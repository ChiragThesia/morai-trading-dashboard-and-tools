## What research settled, and what it explicitly did not

Settled, verified this session by reading the installed package's own signatures:
`argon2-cffi` 25.1.0, `PasswordHasher(time_cost=3, memory_cost=131072, parallelism=1)`,
`type` already defaults to `Type.ID` so it need not be passed, `verify` raises
`VerifyMismatchError` rather than returning False, and `check_needs_rehash` exists.

Not settled: what those parameters cost on Railway. The local numbers are a **floor**, not
the deployed answer. Research reframed CONTEXT.md's question honestly — 128 MiB is trivial
against any Railway plan's memory ceiling, so memory is not the risk; a shared vCPU
slower per-core than Apple Silicon is.

**Fallback order, if the measured Railway time lands meaningfully over 400 ms:** reduce
`time_cost` first, 3 → 2. That stays inside OWASP's documented acceptable range. Only drop
`memory_cost` below OWASP's 19 MiB floor as a genuine last resort, and treat that as a
decision a human makes with the reason written down — these accounts are linked to
brokerage credentials, which is D2-03's whole justification for the higher band.

Raising `parallelism` to 2 roughly halves wall-clock for the same memory and security cost,
but multiplies concurrent memory under simultaneous logins. At four or five users that is
not a real risk, and it is an easy reversible tune — but `parallelism=1` is the cheaper
default and stays the default.

## Package legitimacy

`02-RESEARCH.md`'s Package Legitimacy Audit covers this phase's one new package.
`argon2-cffi`, PyPI, first released 2015, this release 2025-06-03, repo
`github.com/hynek/argon2-cffi`, verdict **OK**, disposition **Approved**. Maintained by the
same maintainer as `attrs` and `structlog`; the reference Python binding for the Argon2
reference implementation. No `[ASSUMED]` or `[SUS]` package exists in this phase, so no
legitimacy checkpoint is required. `pypistats.org` rate-limited the download-count check
this session; research records that as skipped rather than silently omitted.

## Not being built

Rate limiting on the login path. `02-CONTEXT.md` `<deferred>` puts it with the public API
surface, not with identity. It is a real gap and is named as one in the threat register,
not quietly absent.

  <behavior>
    - `hash_password(password: str) -> str` — Argon2id, `time_cost=3`,
      `memory_cost=131072` (KiB, so 128 MiB), `parallelism=1`. One module-level
      `PasswordHasher`, built once; constructing one per call re-pays setup on every login.
    - `verify_password(stored_hash: str, password: str) -> bool` — catches
      `VerifyMismatchError` and returns False. Catches `InvalidHashError` and returns False
      too: a malformed stored hash is a rejected login, not a 500 that tells an attacker
      the row exists.
    - `needs_rehash(stored_hash: str) -> bool` — wraps `check_needs_rehash`, so a later
      parameter change upgrades hashes lazily at next login rather than needing a bulk
      migration that nobody runs.
    - Test: a hashed password verifies against itself.
    - Test: a different password returns False, and does not raise.
    - Test: two hashes of the same password differ — the salt is per-hash.
    - Test: the parameters are read back **out of the produced hash string** (the
      `$argon2id$v=19$m=131072,t=3,p=1$...` prefix), not asserted against the constructor
      arguments. Asserting the argument you just passed proves nothing; parsing the output
      proves the library used it.
    - Test: `needs_rehash` is False for a hash the current hasher produced, and True for one
      produced by a deliberately weaker `PasswordHasher` built inside the test.
    - Test: a malformed hash string returns False rather than raising.
    - Test: neither the password nor the hash appears in `repr()` of anything this module
      exposes, and `verify_password`'s False path emits no log record. `NN-34` applies to a
      password hash exactly as it applies to a token (D2-14).
  </behavior>
