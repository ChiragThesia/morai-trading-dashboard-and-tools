<objective>
The account lifecycle an admin drives by hand: create an account, issue a link that works
once, let the user set a password with it, and reset that password later — with no email
service anywhere in the loop.

Purpose: criterion 1 asks for exactly this, and D2-01 removes an entire vendor, its
deliverability failure modes, and a class of account-takeover surface at the cost of the
admin doing something manual for four or five people they know personally. D2-02 makes the
link a single-use, TTL'd, server-side nonce consumed by one atomic `DELETE ... RETURNING`
— `NN-35`, carried forward verbatim. The atomicity is the point: check-then-update races,
and a setup link that can be used twice is an account-takeover primitive.

Output: the shared token mechanism, three routes, and the bootstrap script without which
nobody can log in at all.
</objective>

<orientation>
## One mechanism, two flows

D2-01 and D2-02 describe the identical mechanism for the setup link and the password
reset. Build it once: one `setup_tokens` table with a `purpose` discriminator column, one
issue function, one consume function. Two tables and two consume functions would be two
implementations of the same atomic-consume logic — the duplicated-write shape this
project's own history warns against, and the same lesson as the money kernel's one carry
source.

## Why `DELETE ... RETURNING` and not anything else

`SELECT` the row, check it is unused, then `UPDATE` a flag or `DELETE` it — that is three
statements with a window between the first and the third where a second request can pass
the same check. A setup link usable twice is an account-takeover primitive. One
`delete().where(token_hash == ..., expires_at > now()).returning(...)` closes the window:
Postgres's own MVCC guarantees exactly one concurrent `DELETE` against a row can succeed,
and the loser's `WHERE` matches zero rows. That is a database guarantee, not something the
application arranges, and criterion 1 requires it tested directly, including concurrently.

`None` back from the consume function means invalid, expired, or already used — deliberately
not distinguished, so the failure mode itself is not an oracle an attacker can query.

## The one place RLS's real cost bites in this phase

Consuming a setup link is an *unauthenticated* request. The user has no session yet — that
is what the link is for. After the token is consumed, the route updates
`users.password_hash`, and `users` carries an RLS policy. With no context set, that UPDATE
matches zero rows and reports success. Nothing raises. The user is told their password was
set and it was not.

This is exactly the failure mode `02-RESEARCH.md`'s "What would have to be true for the
app-level layer to win instead" names as RLS's strongest counter-argument: a query silently
affects fewer rows than expected, with no visible cue. The fix is one line — set
`app.current_user_id` from the consumed row's own `user_id` before the UPDATE — and plan
02-02's `require_rls_context` is what makes forgetting it loud instead of silent. Use it.
There is a test for the silent-failure case specifically, because it is the bug a
reasonable developer ships here.

## No secret is ever returned twice, or logged once

The raw token goes back to the admin in the issue response, once, and only its SHA-256
hash is stored. It never appears in a log line, an error body, a `repr`, or a URL that gets
logged. `NN-34` outranks any decision in this phase (D2-14), and `api/errors.py`'s opaque
envelope plus `_ErrorLocation`'s structural drop of pydantic's `input` key are what keep a
validation failure on these routes from echoing one — which is the code path most likely to
have a token in scope.

## Not being built

No email. Not for creation, not for setup, not for reset. D2-01 is deliberate and permanent
for this milestone. No rate limiting on any of these routes — `02-CONTEXT.md` `<deferred>`
puts it with the public API surface. Both are named in the threat register, not silently
absent.
</orientation>

  <behavior>
    - `TokenPurpose` — a `StrEnum` with `SETUP` and `PASSWORD_RESET`. An enum, not bare
      strings, so a typo in a purpose is a type error rather than a token that can never be
      consumed.
    - `async def issue_token(session, *, user_id, purpose, ttl) -> str` — generates a raw
      token, stores its hash with the purpose and an absolute `expires_at`, returns the raw
      token. The raw token is returned and never stored; the hash is stored and never
      returned.
    - `async def consume_token(session, *, raw_token, purpose) -> UUID | None` — one
      `delete(SetupToken).where(token_hash == hash_token(raw_token), purpose == purpose,
      expires_at > now()).returning(SetupToken.user_id)` statement. Returns the user id, or
      `None` for invalid, expired, already used, or wrong purpose — all four
      indistinguishable to the caller, by design.
    - Test: an issued token consumes once and returns the right user id.
    - Test: the same token consumed a second time returns `None`, and the row is gone from
      the table — asserting both, not just the `None`, so an implementation that flipped a
      flag instead of deleting fails.
    - Test: an expired token returns `None` and its row is left in place, so an expired
      unused token stays distinguishable in the table for anyone debugging.
    - Test: a token issued for `SETUP` returns `None` when consumed as `PASSWORD_RESET`.
      Without this, the `purpose` column is decoration and a reset link would grant initial
      setup or the reverse.
    - Test: **concurrency.** Two `consume_token` calls on two independent sessions and two
      independent engines, launched with `asyncio.gather`, against one token. Exactly one
      returns the user id; the other returns `None`. Criterion 1 requires this tested
      directly. Two sessions on one engine would not prove it — a single connection
      serialises the two statements and the race never happens.
    - Test: neither the raw token nor its hash appears in any log record emitted during any
      of the above.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client → `POST /setup` | A raw token from an untrusted caller is the only credential on this route. |
| admin → another user's account row | The one legitimate cross-user read, and the reason plan 02-04's capability exists. |
| out-of-band channel → the new user | The raw token transits a human channel, by design (D2-01). |
