<objective>
Make the isolation suite capable of failing.

Purpose: this is the phase's equivalent of Phase 1's thirteen-fixture oracle
(`02-CONTEXT.md` `<specifics>` says to treat it that way), and it carries one specific
burden the roadmap's wording does not spell out. A test that only exercises the
application's own query path proves the application's filter, not the policy. If the app
connected as a superuser tomorrow, every RLS policy in the system would go inert and a
naive suite would stay green. Phase 1's `tests/gate/` fixtures set the standard: a gate
that has never rejected anything is decoration.

Output: an isolation suite whose zero-rows claims are made through a connection it has
verified cannot bypass RLS, paired with a superuser arm running identical SQL and
asserting the opposite result; a boot-time gate that kills the web process rather than
serve traffic on a privileged connection; and one small helper that converts RLS's one
genuine cost — silent under-fetching — into a named exception.
</objective>

## The failure this plan exists to prevent

`02-RESEARCH.md` (amended at commit `128d7a2`) separates two claims. The **rule** —
superusers and `BYPASSRLS` roles always bypass row security, and `FORCE ROW LEVEL
SECURITY` binds only the table owner — is quoted from official Postgres documentation and
is solid. The **status** of the live `postgres` role on this Railway instance was inferred,
never queried.

CI has the same problem, and worse: its container runs as `postgresql://morai:morai@...`,
and in the official Postgres image `POSTGRES_USER` is the bootstrap superuser. **A CI
isolation test that connects as `morai` has RLS inert for exactly the same reason
production would, and passes while proving nothing.** Plan 02-01 created `morai_app` and
repointed the app engine at it. This plan makes the suite unable to silently degrade back.

## What makes a zero-rows assertion worth anything

`assert rows == []` is the weakest assertion in software. It passes when the table is
empty, when the table name is misspelled, when the seed fixture silently failed, and when
the policy works. Three of those four are bugs in the test.

So every zero-rows claim in this suite is bracketed:

1. **A privilege precondition.** The connection making the claim reports `rolsuper` false
   and `rolbypassrls` false. Without this, the claim is unfalsifiable.
2. **A positive control.** The identical SQL, through the superuser connection, returns
   every seeded row. This is what proves the query would have found the rows if the policy
   had not excluded them.

Only with both does "zero rows" mean "the policy fired".

## Criterion 3's pooling clause, resolved rather than reinterpreted silently

The roadmap says the suite must pass "against the real Railway pooling configuration
rather than only a direct-connection test container". The phase's own spike answered that
question: **there is no pooling configuration.** Railway's standard Postgres template
accepts direct connections only; PgBouncer is an opt-in feature that has never been added
to this project, confirmed both from Railway's own documentation and from a live read of
the provisioned service's variables (one `DATABASE_URL` to `postgres.railway.internal`, no
unpooled variant). So CI's direct-connection container is the same topology in kind as
Railway's, and the clause is met in substance.

That is a substitution, and Phase 1 set the precedent for how to handle one: state it, do
not silently reinterpret. This plan additionally ships `tools/isolation_smoke.py`, the
deploy-time run against the live service that D2-10 asks for by name. It cannot be run in
this session — deploys are blocked by the permission classifier — so it ships as a
committed, runnable script and an operator step, not as a claim.

## RLS's one real cost, and the cheap thing that makes it louder

`02-RESEARCH.md`'s "What would have to be true for the app-level layer to win instead"
names it honestly: a query that looks like `SELECT * FROM positions` silently returns
fewer rows than expected, and a developer who does not know the table's policy can lose
real time before working out why. That is the strongest legitimate argument for the
familiar app-level alternative, and it was judged not to outweigh the enforcement
guarantee — not dismissed.

Task 3 buys the cheap half of the mitigation: one function, `require_rls_context`, that
turns "zero rows and no idea why" into a named exception at the call site. It is not a
general solution and the plan does not pretend it is. It covers the specific path where
this bites in this phase — code that reads or writes an RLS-protected table outside a
request, where no auth dependency has run. Plan 02-05's setup-token password write is
exactly that path.

      If this test ever fails, the previous test's green is worthless.
    - `test_unset_context_returns_zero_rows` — `app_db_session`, no `SET LOCAL` at all,

      `SELECT current_setting('app.current_user_id', true)` is NULL, so the test says why
      it got zero rows rather than just that it did.
    - `test_context_set_to_a_user_with_no_rows_returns_zero_rows` — a third seeded user who
      owns no probe rows. Distinguishes "the policy excluded rows" from "the context is
      broken and always excludes everything", which the previous two tests together
      otherwise leave open.
    - `test_a_write_for_another_user_is_rejected_by_the_policy` — with context set to A,
      `INSERT INTO gate_user_scoped_probe (user_id, note) VALUES (<B>, ...)` raises. The

      user plant rows in another user's namespace and this is the only thing that catches
      that.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the test suite → its own claims | A suite that cannot fail is the boundary being defended here. |
| process start → serving traffic | The last moment a privileged runtime connection can be caught before it serves a request. |
