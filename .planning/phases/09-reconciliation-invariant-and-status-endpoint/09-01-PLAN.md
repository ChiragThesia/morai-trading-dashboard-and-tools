<objective>
Phase goal (ROADMAP, verbatim): "The core value is enforced and queryable — realised P&L equals the
broker's cash delta, checked every ingest cycle."

This plan is the phase's tracer: the thinnest production-quality path through every layer the phase
touches. A real deferred `sync_user` job, drained by a real worker, reads this user's events and
this user's independently-sourced broker transactions, derives the closed settlement-date trading
days, compares both sides of the invariant on exact `Decimal` arithmetic, and lands a
`reconciliation_runs` row under RLS on the `morai_app` role.

Purpose: nothing in this system has ever checked the invariant it exists to protect, and Phase 7
shipped a feature fully built, unit-tested, merged, and unreachable because `sync_user` never passed
the enabling argument. This plan's verification travels the genuine production call path — defer the
real task by name, drain a real worker, assert the row exists — because a unit test of the pure
function cannot catch that failure and did not.

This plan also resolves `D5-04`, deferred from Phase 5 to here. The oracle's convention is fee-free;
the core value needs a fee-inclusive cash delta. Both cannot be true of the same field. `D9-05`
resolves it by filling the commission from the broker's own payload at reconciliation read-time and
leaving every fee-free field on `events` untouched. If a change in this plan makes the oracle fail,
the change is wrong, never the oracle.

Output: migration 0016, the `ReconciliationRun` model, `src/morai/ledger/reconciliation.py`,
`src/morai/ingest/reconciliation_runs.py`, two named vendor field-name settings, the one-line
`sync_user` seam, and two test files.
</objective>

Research assumptions this plan acts on, named so a later reader sees them:

- **A1 — the vendor field names.** `schwab-py` 1.5.1's installed source contains zero references to
  `netAmount`, `fees` or `commission`; this project's own fixtures never populate them; no public
  source settled it during research, which rates it LOW confidence. The design mitigates rather than
  assumes: both names are injectable settings, and a key that is absent or unparseable makes the
  window `indeterminate` (`D9-08`), never wrongly `passed`. `09-VALIDATION.md` records this as
  Manual-Only; nothing in this plan pretends to verify it locally.
- **A2 — `RECEIVE_AND_DELIVER` carries settlement cash.** If wrong, a real cash movement is excluded
  and the window reports `indeterminate` — the honest direction, bounded by `D9-08`'s own design.
- **A3 — plaintext money columns on `reconciliation_runs`.** Research flagged this for confirmation
  against `CRYPT-02`. Confirmed here and adopted: these are aggregate operational figures about a
  check, the same class as `sync_runs`' row counts, and `D9-13`'s whole point is that a reader can
  answer "how far off, and in which direction" without unwrapping a key. Encrypting them would also
  force a DEK unwrap on every poll of the endpoint `D9-15` requires to be cheap.
- **A4 — commission derived at read-time, never persisted onto `events`.** `09-CONTEXT.md` leaves
  the storage location to Claude's discretion and `09-RESEARCH.md` recommends read-time. Adopted:
  it is the only option that changes zero lines in `pairing.py`'s money arithmetic and zero columns
  on the one table the 13-calendar oracle reads. Recorded as a decision, not an omission.
- **The commission sign.** `D9-05` states the arithmetic literally as `realised − commissions`,
  which assumes the vendor reports a charge as a positive magnitude. The value is read exactly as
  the vendor sends it and never negated, never `abs()`-ed (`NN-9`, `NN-10`). A systematically
  inverted sign fails loudly with both sides stored, which is diagnosable in one place.
</flagged_assumptions>
