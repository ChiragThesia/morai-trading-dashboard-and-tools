<objective>
Phase goal (ROADMAP, verbatim): "The core value is enforced and queryable — realised P&L equals the
broker's cash delta, checked every ingest cycle."

Plan 09-01 made the verdict a fact on disk and plan 09-02 made it a fact worth reading. This plan
makes it queryable, and makes ignoring it a deliberate act.

`GET /reconciliation/status` is one indexed row read of the caller's own latest verdict. It never
recomputes, because recomputing would decrypt every transaction in the window on every poll, and
`API-01` requires the endpoint to be cheap enough to call before rendering anything. `RECON-04` then
asks for more than a reportable failure: while reconciliation is failing, the API must mark the
dependent numbers untrustworthy rather than serving them plain. `D9-14` puts that signal inside the
response envelope, because a signal that lives only in a separate endpoint is one a client forgets
to fetch and then renders a bad number confidently — the exact failure the requirement names.

Output: `src/morai/api/routes_reconciliation.py`, a shared `DependentNumbersModel` base in
`api/models.py`, its application to the one ledger-derived response this API has today, and the
`tests/api/` package this project has not had until now.
</objective>

Assumptions and deliberate ceilings this plan acts on:

- **`trustworthy` reads one row, not a per-window rollup.** `D9-15` is literal: the endpoint reads
  the latest persisted verdict and never recomputes. Taken literally that means a window which
  failed three days ago stops marking the API untrustworthy once a later window passes. That is a
  real ceiling, it is chosen rather than overlooked, and the alternative — a per-window latest-row
  rollup — is a window function, not the one indexed row read `API-01` asks for. Named at the code
  in `reconciliation_trustworthy`'s own docstring with the rollup as its upgrade path, so a later
  reader meets the limit where it lives.
- **`PositionResponse` is the only response in this API today carrying a ledger-derived number.**
  Its `opened_at` is derived from the event stream. Phase 11's review surface is where the rest
  land, and it inherits `DependentNumbersModel` rather than re-deciding this.
