<objective>
Phase goal (ROADMAP, verbatim): "The core value is enforced and queryable — realised P&L equals the
broker's cash delta, checked every ingest cycle."

Plan 09-01 made the verdict a fact on disk and plan 09-02 made it a fact worth reading. This plan
makes it queryable, and makes ignoring it a deliberate act.

`GET /reconciliation/status` is one indexed query over the caller's own per-window verdicts. It
never recomputes, because recomputing would decrypt every transaction in the window on every poll,
and `API-01` requires the endpoint to be cheap enough to call before rendering anything. `D9-15`'s
"read the latest persisted verdict, never recompute" is a cost instruction, and this plan honours the
cost while reading the right rows: `trustworthy` is false while ANY window is still unresolved, not
merely while the newest one is.

That distinction is the requirement, not a refinement of it. `RECON-04` says the API marks dependent
numbers untrustworthy rather than serving them plain. Deriving the signal from the most recent row
alone would let a window that failed three days ago and was never repaired be cleared by any later
window that passed — and a client would then render a P&L spanning the broken window as trustworthy,
which is the exact failure the requirement names. `D9-03` supplies the resolution rule: a re-check is
a new row rather than an edit, so a window is resolved when a later run for that same `trading_day`
returns `passed`, and outstanding otherwise.

`D9-14` then puts that signal inside the response envelope, because a signal that lives only in a
separate endpoint is one a client forgets to fetch and then renders a bad number confidently.

Output: `src/morai/api/routes_reconciliation.py`, a shared `DependentNumbersModel` base in
`api/models.py`, its application to the one ledger-derived response this API has today, and the
`tests/api/` package this project has not had until now.
</objective>

- **`trustworthy` reads every window's latest verdict, not the latest row.** An earlier draft of
  this plan derived the signal from the single most recent run and recorded the resulting hole — an
  old unrepaired failure cleared by a later pass — as a known ceiling. That was wrong: the ceiling
  defeats `RECON-04`, and it bought nothing, because `DISTINCT ON (trading_day) ... ORDER BY
  trading_day, checked_at DESC` is still one indexed scan on the index migration 0016 already
  carries for the reopening lookup. No window function, no second index, no recompute. The correct
  behaviour and the cheap read were never in tension; the literal reading of `D9-15` only made them
  look like they were.
- **`PositionResponse` is the only response in this API today carrying a ledger-derived number.**
  Its `opened_at` is derived from the event stream. Phase 11's review surface is where the rest
  land, and it inherits `DependentNumbersModel` rather than re-deciding this.

Define `ReconciliationStatusResponse(DependentNumbersModel)` with
`last_run: ReconciliationRunSummary | None` and `unresolved_run: ReconciliationRunSummary | None`.
It inherits `trustworthy` from the base Task 2 adds to `api/models.py`; if Task 2 has not landed
yet, define the base first — it is four lines and both tasks need it.

Two run fields, not one, and they answer different questions. `last_run` answers "when was the
ledger last checked, and what did that check say" — a client polling before it renders needs to know
whether the answer is fresh. `unresolved_run` answers "which window is still wrong", and it is what
makes `trustworthy` false actionable: without it, a caller told the numbers are untrustworthy while
the most recent run passed has no way to learn why, which is `RECON-03`'s own requirement that a
failure name its window. In the common case both are null or `unresolved_run` is null and the client
renders freely.

Define `summarise_run(record: ReconciliationRunRecord) -> ReconciliationRunSummary`, composing the
body field by field from the record, never by handing an ORM row or a dataclass to the serialiser —
`/schwab/sync-runs`' own stated convention, which is what keeps an optional value optional on the
wire instead of silently defaulted.

Define a frozen dataclass `ReconciliationStanding` with `trustworthy: bool`,
`latest: ReconciliationRunRecord | None` and `oldest_unresolved: ReconciliationRunRecord | None`,
and `reconciliation_standing(session: AsyncSession, user_id: UUID) -> ReconciliationStanding` that
computes all three from one call to `read_window_verdicts` and no second query. `latest` is the
member with the greatest `checked_at`; `oldest_unresolved` is the member with the smallest
`trading_day` whose verdict is not `PASSED`; `trustworthy` is true exactly when
`oldest_unresolved` is `None` and `latest` is not `None`.

Say in the docstring what each branch means and why, because every one of them is a requirement
rather than a preference. A `failed` window is untrustworthy for the obvious reason. An
`indeterminate` window is untrustworthy because a check that could not be answered has certified
nothing — `D9-08`'s discipline carried up to the API. No run at all is untrustworthy because a
ledger nobody has checked is not a ledger anybody should render numbers from. And an *older*
unresolved window is untrustworthy even when the newest window passed, because a client rendering a
P&L that spans the broken window would be serving exactly the number `RECON-04` forbids serving
plain — a later window passing says nothing about an earlier one that was never repaired.

State the resolution rule in the same docstring, concretely rather than by implication: a window is
resolved when a later run for that same `trading_day` returns `passed`, and outstanding otherwise.
`D9-03` makes a re-check a new row rather than an edit, so `read_window_verdicts`' one-record-per-
window result is where superseding actually happens — this function only reads it. Without that
rule, `D9-03`'s own reopening would leave a repaired window marked untrustworthy forever, which
would train the reader to ignore the signal exactly as `D9-08` warns.

State the cost too, since `API-01` is what makes it a requirement: this is one indexed scan on
`ix_reconciliation_runs_user_id_trading_day_checked_at`, whose order the `DISTINCT ON` matches, so
there is no sort node, no window function, no second index and no decryption. Reading each window's
latest verdict is not more expensive than reading the newest row; it was only ever a different
query.
