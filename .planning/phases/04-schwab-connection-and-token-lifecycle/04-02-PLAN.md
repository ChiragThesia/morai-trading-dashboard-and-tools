<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `GET /schwab/callback` | Unauthenticated; the query string carries a bearer-equivalent authorization code and the CSRF state. |
| app → captured log output | Anything the app logs can reach Railway's log stream and PostHog. |
| one user's callback → another user's connection row | Under concurrency, a payload swap here is silent. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Spoofing | A `state` replayed after a successful callback | critical | mitigate | Route-level replay proven rejected with 400 and no second row; the atomic consume proven at the `consume_token` level with two independent engines under `asyncio.gather` (Task 1, `NN-35`, ASVS 5.0 V3). |
| T-04-10 | Information Disclosure | The rejection path acting as an oracle — distinguishing unknown from expired from replayed | medium | mitigate | All three asserted identical in status and body (Task 1), matching `consume_token`'s own documented design that the four failure causes are indistinguishable to the caller. |
| T-04-11 | Information Disclosure | The authorization code, received URL or state reaching a log record or a response body | critical | mitigate | Capture over the root, vendor, HTTP-client and OAuth-library loggers at DEBUG across success, rejection and exception paths, asserting absence in both log text and body (Task 2, `NN-34`, ASVS 5.0 V14). |
| T-04-12 | Information Disclosure | Hypercorn's access log rendering the callback query string in production | high | accept | Structurally unobservable from an in-process ASGITransport suite. Stays a Manual-Only item in 04-VALIDATION.md, with the limit stated in the test docstring and the SUMMARY rather than papered over by a test that cannot see it. |
| T-04-13 | Tampering | Two concurrent callbacks crossing payloads, landing user A's token on user B's row | high | mitigate | Barrier-enforced overlap plus a per-row account-hash cross-check, so a swap fails the assertion rather than passing as "two rows exist" (Task 1). |
| T-04-14 | Tampering | Re-auth accumulating a second row, making "which connection is live" ambiguous | high | mitigate | Per-user `SELECT count(*)` asserted at exactly 1 across re-auth and expired-then-repaired flows (Task 3, D4-09). |
</threat_model>
