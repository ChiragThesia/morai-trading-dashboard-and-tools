<objective>
Serialise a user's token refreshes on that user's own lock, and prove the scoping with a
positive control: user A's refresh must not block user B's.

Purpose: v1 held one global lock for one user. Five users need five independent locks, not
one queue. The failure a global lock produces is not an error — it is a system that works
and gets slower with every user, which no naive "concurrent refreshes don't corrupt" test
would ever catch. The second test in this plan is the real content; the first alone passes
under exactly the bug this requirement exists to prevent.

Output: a `SchwabClient` obtained only through a lock-holding async context manager in
`src/morai/vendor/connections.py`, the adapter's `client_from_access_functions` wiring with
plain synchronous token closures over an in-memory holder, and
`tests/vendor/test_refresh_lock.py` carrying both positive controls.
</objective>

    Add one method to the `SchwabAuth` Protocol in `src/morai/vendor/protocol.py`: build a
    `SchwabClient` from a token holder, given synchronous read and write callables. Three
    methods now, all three actually called — the only-what-we-use rule (D4-02) is about not
    naming methods the project does not call, not about a fixed count.

    Add a small mutable `TokenHolder` beside it: it carries the current token value, records
    whether the vendor ever wrote a new one, and exposes a plain `def` reader and a plain
    `def` writer. **Both must be plain `def`, never `async def`.** Verified against the real
    1.5.1 wheel: the library calls these closures with no `await` anywhere in `schwab/auth.py`,
    even on the `asyncio=True` path, so an `async def` closure produces a coroutine that is
    assigned, never awaited, and discarded — a silently-skipped token write with nothing but
    a garbage-collection-time RuntimeWarning to show for it. Put that reason in a comment at
    the closures themselves, so a later reader making them async for consistency meets the
    warning rather than the bug.

    Implement the real method in `src/morai/vendor/schwab_adapter.py` over
    `client_from_access_functions`, wrapping the synchronous construction in
    `asyncio.to_thread` for the same reason the exchange path already does.

    Add an async context manager to `src/morai/vendor/connections.py` that yields a
    `SchwabClient` for one user, holding that user's own lock for the whole body. The order
    inside it is the requirement, not an implementation detail:

    First, `SELECT pg_advisory_xact_lock(hashtext(:uid))` with the user id bound as a
    parameter — verified live against local Postgres 18, including with a bound parameter
    rather than a literal, and the same primitive `tools/create_admin.py` already uses.
    Transaction-scoped, so it releases on the caller's commit or on a crash, with no
    separate unlock to forget. Not `SELECT ... FOR UPDATE` on the token row: that would work
    here, since unlike `create_admin`'s case the row exists, but it holds a row lock across
    the refresh's network call (D4-10).

    Second — and only after the lock is granted — read and decrypt the stored token. Reading
    before locking is the bug this ordering exists to prevent: a waiter that loaded the token
    first would present the value the winner has already rotated away from, and Schwab
    answers a stale refresh token with `invalid_grant`. Write that sentence into the code.

    Third, yield the client built over a `TokenHolder` seeded with that token. Fourth, after
    the body returns, if the holder shows the vendor wrote a new token, re-encrypt it under
    the user's current DEK and `UPDATE` the row — `token_ciphertext`, `token_nonce` and
    `key_version` only. **Leave `token_created_at` alone:** it is the vendor's own
    `creation_timestamp`, which `schwab-py` explicitly does not update on refresh, and moving
    it here would reset the seven-day clock on every automatic refresh and make the expiry
    invisible. Do not commit — the caller owns the transaction (D4-20), and here that is not
    a style choice twice over: the lock's lifetime and the write's durability are the same
    transaction, deliberately.

    Record the collision arithmetic in the docstring rather than defending against it:
    `hashtext` returns an int4, so for a handful of users the birthday-style collision
    probability is on the order of `10 / 2^32`. A collision would cause a false extra
    serialisation between two unrelated users — safe, briefly slower — and never a false
    sharing of token data, since the key gates a critical section and is never a join key or
    a cache key.

    Write `tests/vendor/test_refresh_lock.py`'s first test. Two independent engines, two
    independent sessions, `asyncio.gather` — two sessions on one engine would not prove
    anything, because a single connection serialises the statements and the race never
    happens, exactly as `test_concurrent_consume_produces_exactly_one_winner`'s docstring
    already says. Have the fake rotate the refresh token on each use and raise its
    `invalid_grant` error if it is ever presented a value it has already rotated away from,
    so the test fails loudly rather than silently passing if the lock were absent. Assert
    both calls completed, neither raised, and the fake's recorded entry and exit times for
    the two critical sections do not overlap. Wrap the gather in an explicit timeout.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two concurrent app requests → one user's token row | The refresh race lives here; the vendor answers a stale refresh token with `invalid_grant` and the user's connection dies. |
| app process → Postgres advisory lock namespace | The lock key is derived from the user id; a constant key silently degrades every user into one queue. |
| adapter → vendor token callbacks | A synchronous callback boundary inside an async codebase, where a wrong signature loses the write with no error. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-15 | Tampering | Two concurrent refreshes racing on one user's token, producing `invalid_grant` and killing the connection | high | mitigate | `pg_advisory_xact_lock(hashtext(user_id))` acquired before the token read, released with the caller's transaction (D4-10, Task 1); the fake raises `invalid_grant` on a stale token so an absent lock fails the test loudly. |
| T-04-16 | Denial of Service | A constant or shared lock key serialising every user's refresh behind every other user's | high | mitigate | The A-does-not-block-B ordering assertion plus a direct assertion that the two users' lock keys differ (Task 2, CONN-06). |
| T-04-17 | Repudiation | A rotated token silently never persisting because the write closure was `async def` | high | mitigate | Plain `def` closures over a `TokenHolder`, with the persist performed from the caller's async code after the vendor call returns; durability asserted by reading the row back through an independent session (Task 1). |
| T-04-18 | Tampering | A refresh advancing `token_created_at` and resetting the seven-day expiry clock | medium | mitigate | The update touches ciphertext, nonce and key version only; `token_created_at` asserted unchanged after a refresh (Task 1, D4-12). |
| T-04-19 | Denial of Service | A lock held across a network call leaking on a crashed process | medium | mitigate | Transaction-scoped advisory lock, released on commit or on connection loss, with no separate unlock path to fail (D4-10). |
</threat_model>
